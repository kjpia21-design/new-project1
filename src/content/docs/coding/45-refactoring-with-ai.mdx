## What you'll be able to do after this tutorial

- Explain what refactoring is and why a passing test run before you start matters.
- Ask Claude for a plan, read it, and approve only the part you want.
- Work in small steps, with a test run and a commit after each one.
- Go back to a known good state with `/rewind` or Git when a step goes wrong.

## Concepts to know first

**Refactoring** means changing how code is organized (names, structure, duplicated parts) without changing what it does. That is why tests matter: if the same tests pass before and after, you have some evidence that behavior did not change. A test only covers what it checks, so passing tests are evidence, not proof. [1. Getting started with Claude Code](/coding/06-claude-code-start/) shows how to start. For the commit and branch habits used here, see [Coding 17](/coding/44-git-with-claude-code/). For finding the cause of a failing test, see [Coding 16](/coding/43-debugging-with-ai/), and for having the finished change reviewed, [Coding 15](/coding/42-code-review-ai/).

<Aside type="caution" title="Refactoring should not change behavior">
If a "refactor" also adds features or fixes bugs, you can no longer tell whether a failing test points to a mistake or an intended change. Keep behavior changes in separate commits. Never let Claude delete or weaken a test just to make it pass.
</Aside>

## Step-by-step guide

<Steps>

1. **Make a safe starting point**

   In your own terminal, create a branch and confirm that your working tree is clean:

   ```bash
   git switch -c refactor-utils
   git status
   ```

   Commit or stash anything unfinished first, so every later change in the diff comes from this refactor.

2. **Run the tests before changing anything**

   The best-practices page explains why a check matters: with nothing to run, "looks done" is all Claude has, and you become the test suite. Run your project's test command yourself (for example `npm test`; use whatever your project uses) and note the result. If the tests already fail, fix that first or write down which ones fail, so you do not blame the refactor later. If your repo has no tests, ask Claude to add some for the code you will touch, as a separate step and commit. The common-workflows page has a "Work with tests" recipe for this, which we did not follow in detail.

3. **Find what to refactor**

   The official recipe starts with a question, not an edit, for example "find deprecated API usage in our codebase". Try a read-only prompt of your own:

   <PromptBox>
   Look at utils.js. Do not edit anything. List the functions that are long, repeated or hard to read, and for each say what is wrong in one sentence. Rank them by how risky they would be to change, safest first. Say which of them have tests and which do not.
   </PromptBox>

4. **Ask for a plan before edits**

   For changes you want to review before they touch disk, the common-workflows page points to plan mode. Start with `claude --permission-mode plan`, or press Shift+Tab during a session until the status bar shows plan mode. In that mode Claude reads files and proposes a plan, and makes no edits until you approve. A prompt to use:

   <PromptBox>
   Propose a plan to refactor the safest function first. Break it into steps that each change one thing and can be tested alone. For each step, say which files change and how I can check that behavior stayed the same. Do not include any behavior change or new feature.
   </PromptBox>

   Read the plan. Cross out steps you do not want. The docs mention that you can edit the plan in your text editor; we did not try this.

5. **Do one small step**

   The official tips say to do refactoring in small, testable increments. Approve only the first step, and ask for the check in the same prompt:

   <PromptBox>
   Do step 1 only: extract the repeated date formatting into one helper function and use it where it was repeated. Keep the behavior the same. Then run the tests and show me the command you ran and its output. If a test fails, stop and tell me instead of changing the test.
   </PromptBox>

   Asking for "the command it ran and its output" follows the best-practices advice to ask for evidence. Then run the tests yourself too.

6. **Read the diff, then commit**

   In your own terminal:

   ```bash
   git diff     # every changed line
   git status   # any file you did not expect
   ```

   Check that no test file changed unless you asked for it. If it looks right, commit with a message that says it is a refactor with no behavior change, for example `git commit -am "Extract date formatting helper"`. Using `-am` only stages files Git already tracks; use `git add <files>` for new files. Then go back to step 5 for the next step.

7. **Review the whole change**

   When the plan is finished, run the tests once more, then ask for a fresh look. The best-practices page says `/code-review` reviews the diff in a fresh subagent that never saw your conversation. You can also write your own review prompt:

   <PromptBox>
   Compare this branch with main. List every place where behavior might have changed, even slightly, such as different error handling, ordering, default values or rounding. Do not edit anything.
   </PromptBox>

8. **Go back when a step goes wrong**

   Pick the layer that matches the damage:

   | Situation | What to use |
   | --- | --- |
   | Claude is heading the wrong way | `Esc` to stop it |
   | Claude's file edits in this session were wrong | `/rewind` (or `Esc` twice on an empty prompt) to roll back code, conversation or both |
   | A file was changed only by a Bash command | Checkpoints do not track it; use Git, such as `git restore <file>` |
   | The step is committed but wrong | `git revert <commit>` adds a new commit that undoes it (standard Git) |
   | Everything on the branch is wrong | Switch back to `main` and delete the branch (standard Git); nothing else was touched |

   The checkpointing page says checkpoints are for quick session-level recovery and that Git remains the tool for commits and long-term history.

</Steps>

## Quick reference

| Task | Command or place |
| --- | --- |
| New branch | `git switch -c <name>` |
| Plan mode at start | `claude --permission-mode plan` |
| Plan mode in a session | Shift+Tab until the status bar shows plan mode |
| Ask for proof | "show me the command you ran and its output" |
| Roll back Claude's edits | `/rewind` or `Esc` twice on an empty prompt |
| Review the diff | `/code-review` |
| Undo a commit safely | `git revert <commit>` |

## Common problems

### Tests fail after a step

- **Cause**: The step changed behavior, or the tests were already failing.
- **Fix**: Compare with your note from step 2. If the step caused it, roll it back with `/rewind` or Git and ask for a smaller step. Do not accept a change to the test unless the old expectation was truly wrong.

### Claude changed the tests to make them pass

- **Cause**: It treated the failing test as the problem.
- **Fix**: Say in the prompt that tests must not be edited unless you agree. Check `git diff` for test files and restore them with `git restore <file>`.

### The diff is far bigger than I expected

- **Cause**: The step covered too much, or formatting changes were mixed in.
- **Fix**: Roll back and ask for one change at a time. Keep formatting-only changes in their own commit.

### /rewind did not undo a change

- **Cause**: The file was changed only by a Bash command, which checkpoints do not track.
- **Fix**: Use Git: `git restore <file>`, or go back to the last commit.

### There are no tests at all

- **Cause**: Nothing can confirm that behavior stayed the same.
- **Fix**: Add a few tests for the code you will change first, in a separate commit, or refactor only very small, obvious pieces and check them by hand.

## Practical tips

- Practice in a throwaway repository before touching real work.
- One idea per commit makes `git revert` easy.
- A green test run is evidence, not a guarantee. Check anything the tests do not cover by hand.
- Do not refactor and add features in the same step.
- Re-check commands and keys against the official pages, since Claude Code changes often.
