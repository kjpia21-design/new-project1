- 공식 리팩터링 레시피는 네 단계예요. 리팩터링할 오래된 코드를 찾고, 개선 제안을 받고, "동작은 그대로 유지하면서" 변경을 적용하고, 테스트를 돌려요. 팁에는 리팩터링을 "작고 테스트 가능한 단위"로 하라는 내용이 있어요.
- 모범 사례 페이지는 Claude가 일이 끝난 것처럼 보이면 멈춘다고 해요. 그래서 통과·실패로 답이 나오는 확인 수단(테스트 파일, 빌드 종료 코드, 린터)을 주고, 실행한 명령과 출력을 증거로 달라고 하라고 해요.
- 디스크에 닿기 전에 검토하고 싶은 변경에는 common-workflows 페이지가 계획 모드를 권해요. Claude가 파일을 읽고 계획을 제안하되, 내가 승인하기 전에는 수정하지 않아요. `claude --permission-mode plan`으로 시작하거나 상태 표시줄에 계획 모드가 보일 때까지 Shift+Tab을 눌러요.
- 되돌리려면 `/rewind`가 Claude가 자체 도구로 고친 파일을 되돌려요. 체크포인트 페이지는 체크포인트가 세션 단위 복구용이고 커밋과 장기 이력은 계속 Git을 쓰라고 해요.
- 2026-11-04에 공식 페이지 세 곳을 읽었어요. 이 튜토리얼을 위해 Claude Code를 직접 실행해 보지는 않았어요. 프롬프트, "테스트 먼저"라는 순서, Git 명령은 우리 조언이거나 일반 Git 사용법이고 공식 규칙이 아니에요.
</Summary>

## 이 튜토리얼로 할 수 있게 되는 것

- 리팩터링이 무엇인지, 시작 전에 테스트가 통과하는 상태가 왜 중요한지 설명할 수 있어요.
- Claude에게 계획을 받아 읽어 보고, 원하는 부분만 승인해요.
- 작은 단계로 나눠 진행하고, 단계마다 테스트와 커밋을 해요.
- 단계가 잘못되면 `/rewind`나 Git으로 멀쩡했던 상태로 돌아가요.

## 먼저 알아둘 개념

**리팩터링**은 코드가 하는 일은 바꾸지 않고 이름, 구조, 중복 같은 짜임새를 정리하는 일이에요. 그래서 테스트가 중요해요. 같은 테스트가 전후에 모두 통과하면 동작이 바뀌지 않았다는 증거가 되기 때문이에요. 다만 테스트는 확인하는 부분만 보장하므로, 통과는 증거일 뿐 증명은 아니에요. [1. Claude Code 시작하기](/ko/coding/06-claude-code-start/)에서 시작 방법을 볼 수 있어요. 여기서 쓰는 커밋·브랜치 습관은 [17편](/ko/coding/44-git-with-claude-code/), 실패하는 테스트의 원인 찾기는 [16편](/ko/coding/43-debugging-with-ai/), 끝낸 변경의 리뷰는 [15편](/ko/coding/42-code-review-ai/)을 참고하세요.

<Aside type="caution" title="리팩터링은 동작을 바꾸지 않아야 해요">
"리팩터링"하면서 기능을 추가하거나 버그를 같이 고치면, 테스트가 실패했을 때 실수인지 의도한 변경인지 구분할 수 없어요. 동작 변경은 별도 커밋으로 하세요. 테스트를 통과시키려고 Claude가 테스트를 지우거나 약하게 만들게 두지 마세요.
</Aside>

## 단계별 따라 하기

<Checklist items={[
  '연습용 저장소의 별도 브랜치에서 작업 중이다',
  '변경을 부탁하기 전에 테스트가 통과했다',
  '수정을 승인하기 전에 계획을 요청해서 읽었다',
  '단계마다 작게 하고, 테스트와 커밋을 했다',
  '테스트를 통과시키려고 테스트를 지우거나 약하게 만들지 않았다',
]} />

<Steps>

1. **안전한 출발점 만들기**

   내 터미널에서 브랜치를 만들고 작업 폴더가 깨끗한지 확인하세요.

   ```bash
   git switch -c refactor-utils
   git status
   ```

   끝내지 못한 작업은 먼저 커밋하거나 보관해 두세요. 그래야 이후 diff의 변경이 모두 이번 리팩터링에서 나온 것이에요.

2. **바꾸기 전에 테스트부터 돌리기**

   모범 사례 페이지는 확인 수단이 왜 필요한지 설명해요. 돌려 볼 것이 없으면 Claude에게는 "끝난 것 같다"는 판단뿐이고, 내가 테스트 역할을 하게 돼요. 프로젝트의 테스트 명령을 직접 실행하고(예: `npm test`, 프로젝트마다 달라요) 결과를 적어 두세요. 이미 실패하는 테스트가 있으면 먼저 고치거나 어떤 것이 실패하는지 기록해서, 나중에 리팩터링 탓으로 오해하지 않게 하세요. 테스트가 없다면 고칠 코드에 대한 테스트를 Claude에게 먼저 추가하게 하되, 별도 단계와 별도 커밋으로 하세요. common-workflows 페이지에 "Work with tests" 레시피가 있는데 자세히 따라 해 보지는 않았어요.

3. **무엇을 정리할지 찾기**

   공식 레시피는 수정이 아니라 질문으로 시작해요. 예를 들면 "find deprecated API usage in our codebase"예요. 읽기만 하는 프롬프트를 직접 써 보세요.

   <PromptBox>
   utils.js를 살펴봐 줘. 아무것도 수정하지 마. 길거나, 반복되거나, 읽기 어려운 함수를 나열하고 각각 무엇이 문제인지 한 문장으로 적어 줘. 바꿨을 때 위험한 정도로 순위를 매기고, 가장 안전한 것부터 보여 줘. 그중 테스트가 있는 것과 없는 것도 알려 줘.
   </PromptBox>

4. **수정 전에 계획 받기**

   디스크에 닿기 전에 검토하고 싶은 변경에는 common-workflows 페이지가 계획 모드를 안내해요. `claude --permission-mode plan`으로 시작하거나, 세션 중에 상태 표시줄에 계획 모드가 보일 때까지 Shift+Tab을 누르세요. 이 모드에서 Claude는 파일을 읽고 계획을 제안하며, 내가 승인하기 전에는 수정하지 않아요. 쓸 프롬프트예요.

   <PromptBox>
   가장 안전한 함수부터 리팩터링하는 계획을 제안해 줘. 단계마다 한 가지만 바꾸고 따로 테스트할 수 있게 나눠 줘. 각 단계마다 바뀌는 파일과, 동작이 그대로인지 내가 확인하는 방법을 적어 줘. 동작 변경이나 새 기능은 넣지 마.
   </PromptBox>

   계획을 읽고, 원하지 않는 단계는 빼세요. 문서에는 계획을 텍스트 편집기에서 고칠 수 있다는 언급이 있는데, 직접 해 보지는 않았어요.

5. **작은 단계 하나만 하기**

   공식 팁은 리팩터링을 작고 테스트 가능한 단위로 하라고 해요. 첫 단계만 승인하고, 같은 프롬프트에서 확인까지 요청하세요.

   <PromptBox>
   1단계만 해 줘. 반복되는 날짜 서식 처리를 헬퍼 함수 하나로 빼고, 반복되던 곳에서 그 함수를 쓰게 해 줘. 동작은 그대로 유지해. 그다음 테스트를 실행하고, 실행한 명령과 출력을 보여 줘. 테스트가 실패하면 테스트를 바꾸지 말고 멈춰서 알려 줘.
   </PromptBox>

   "실행한 명령과 출력"을 달라는 것은 모범 사례 페이지의 증거 요청 조언을 따른 거예요. 그다음 테스트를 내가 직접 한 번 더 돌려 보세요.

6. **diff를 읽고 커밋하기**

   내 터미널에서 해요.

   ```bash
   git diff     # 바뀐 모든 줄
   git status   # 예상하지 못한 파일
   ```

   요청하지 않았는데 테스트 파일이 바뀌지 않았는지 확인하세요. 괜찮으면 동작 변화 없는 리팩터링이라는 점이 드러나게 커밋해요. 예: `git commit -am "Extract date formatting helper"`. `-am`은 Git이 이미 추적하는 파일만 스테이징하므로, 새 파일은 `git add <파일>`을 쓰세요. 그다음 5단계로 돌아가 다음 단계를 진행하세요.

7. **전체 변경 검토하기**

   계획이 끝나면 테스트를 한 번 더 돌리고 새로운 시선으로 검토를 받으세요. 모범 사례 페이지에 따르면 `/code-review`는 대화를 보지 못한 새 서브에이전트가 diff를 리뷰해요. 직접 리뷰 프롬프트를 써도 돼요.

   <PromptBox>
   이 브랜치를 main과 비교해 줘. 동작이 조금이라도 달라졌을 수 있는 곳을 모두 나열해 줘. 오류 처리, 순서, 기본값, 반올림 같은 거야. 아무것도 수정하지 마.
   </PromptBox>

8. **잘못되면 되돌리기**

   피해에 맞는 방법을 고르세요.

   | 상황 | 사용할 것 |
   | --- | --- |
   | Claude가 엉뚱한 쪽으로 가고 있다 | `Esc`로 멈추기 |
   | 이 세션에서 Claude가 고친 파일이 잘못됐다 | `/rewind`(또는 빈 프롬프트에서 `Esc` 두 번)로 코드·대화·둘 다 되돌리기 |
   | Bash 명령으로만 바뀐 파일이다 | 체크포인트가 추적하지 않음. Git 사용 (`git restore <파일>`) |
   | 커밋했는데 그 단계가 잘못됐다 | `git revert <커밋>`이 되돌리는 새 커밋을 추가 (일반 Git) |
   | 브랜치 전체가 잘못됐다 | `main`으로 돌아가 브랜치를 삭제 (일반 Git). 다른 것은 건드리지 않았어요 |

   체크포인트 페이지는 체크포인트가 빠른 세션 단위 복구용이고, 커밋과 장기 이력은 계속 Git을 쓰라고 해요.

</Steps>

## 자주 겪는 문제

### 한 단계 뒤에 테스트가 실패해요

- **원인**: 그 단계가 동작을 바꿨거나, 원래 테스트가 실패하고 있었어요.
- **해결**: 2단계에서 적어 둔 기록과 비교하세요. 그 단계가 원인이면 `/rewind`나 Git으로 되돌리고 더 작은 단계로 다시 요청하세요. 예전 기대값이 정말 틀렸던 경우가 아니면 테스트 변경을 받아들이지 마세요.

### Claude가 테스트를 통과시키려고 테스트를 바꿨어요

- **원인**: 실패한 테스트 자체를 문제로 본 거예요.
- **해결**: 내가 동의하기 전에는 테스트를 수정하지 말라고 프롬프트에 적으세요. `git diff`에서 테스트 파일을 확인하고 `git restore <파일>`로 되돌리세요.

### diff가 예상보다 훨씬 커요

- **원인**: 한 단계가 너무 많은 걸 다뤘거나 서식 변경이 섞였어요.
- **해결**: 되돌리고 한 번에 한 가지씩 요청하세요. 서식만 바꾸는 변경은 별도 커밋으로 두세요.

### /rewind로 변경이 되돌아가지 않았어요

- **원인**: Bash 명령으로만 바뀐 파일이라 체크포인트가 추적하지 않아요.
- **해결**: Git을 쓰세요. `git restore <파일>`이나 마지막 커밋으로 돌아가세요.

### 테스트가 전혀 없어요

- **원인**: 동작이 그대로인지 확인해 줄 것이 없어요.
- **해결**: 고칠 코드에 대한 테스트를 별도 커밋으로 먼저 추가하거나, 아주 작고 분명한 부분만 리팩터링하고 직접 확인하세요.

## 실전 팁

- 실제 작업에 손대기 전에 버려도 되는 저장소에서 먼저 연습하세요.
- 아이디어 하나에 커밋 하나면 `git revert`가 쉬워요.
- 테스트 통과는 증거이지 보장이 아니에요. 테스트가 다루지 않는 부분은 직접 확인하세요.
- 리팩터링과 기능 추가를 같은 단계에서 하지 마세요.
- Claude Code는 자주 바뀌니 명령과 단축키는 공식 페이지에서 다시 확인하세요.
