<Summary>
- AI 리뷰는 **1차 점검**이지 사람 리뷰의 대체가 아니에요. Claude 공식 문서도 버그나 보안 취약점을 놓칠 수 있고, 지적 사항이 없다고 해서 코드에 오류가 없거나 안전하다는 뜻은 아니라고 해요. 병합 결정은 팀이 해요.
- 네 가지 방법을 다뤄요. 내 Claude Code 세션의 `/code-review`(모든 플랜), 관리형 **Code Review** 서비스(Team·Enterprise 플랜, GitHub 저장소, Owner가 켜야 해요), 직접 만든 **GitHub Actions** 워크플로, 풀 리퀘스트의 **GitHub Copilot 코드 리뷰**예요.
- 코드가 가는 곳은 방법마다 달라요. 관리형 Code Review는 Anthropic 인프라에서, GitHub Actions는 GitHub 러너와 Claude API로, Copilot 코드 리뷰는 GitHub를 통해 돌아가요. 회사 규정을 확인하고, 비밀 정보가 든 코드는 보내지 마세요.
- 저장소의 파일로 리뷰 방향을 잡을 수 있어요. Claude는 `CLAUDE.md`·`REVIEW.md`, Copilot은 `.github/copilot-instructions.md` 등이에요.
- 2026-11-02에 공식 페이지를 읽었어요. `/code-review`를 실행하거나 워크플로를 설정하거나 Copilot 리뷰를 요청해 보지는 않았어요. 아래 명령과 동작은 모두 문서 내용이에요.
</Summary>

## 이 튜토리얼로 할 수 있게 되는 것

- 브랜치, 풀 리퀘스트 번호, 폴더에 `/code-review`를 실행하고 `--fix`와 `--comment`가 무엇을 바꾸는지 알기
- 네 가지 리뷰 방법이 어디서 돌고, 누가 쓸 수 있고, 무엇을 건드리는지 구분하기
- 팀이 중요하게 보는 부분에 리뷰가 집중하도록 안내 파일 쓰기
- AI 지적을 확인해야 할 단서로 다루고, 병합 책임은 사람이 지기

## 먼저 알아둘 개념

**풀 리퀘스트**(PR)는 내 브랜치를 다른 브랜치에 합치자는 제안이고, 리뷰는 합쳐지기 전에 누군가 변경 내용을 읽는 단계예요. [코딩 3](/ko/coding/08-cloud-github/)에서 Claude Code가 GitHub와 함께 일하는 모습을 볼 수 있어요. [코딩 13](/ko/coding/40-settings-permissions/)은 `--fix`가 내 파일을 고칠 수 있는지를 정하는 권한 모드를 설명해요. [개발 7](/ko/dev/07-headless-ci/)은 GitHub Actions에서 Claude Code를 자동으로 돌리는 방법을 다뤄요.

### 방법 비교 (공식 문서, 2026-11-02)

| 방법 | 시작하는 방식 | 돌아가는 곳 | 쓸 수 있는 사람 |
| --- | --- | --- | --- |
| `/code-review` | Claude Code에서 직접 입력 | 내 Claude Code 세션 | 모든 플랜의 누구나 |
| Code Review(관리형) | 저장소별 설정에 따른 PR 활동, 또는 `@claude review` 댓글 | Anthropic 인프라 | Team·Enterprise 플랜, GitHub 저장소, Owner가 켠 뒤 |
| 내 CI에서 Claude | 파이프라인 이벤트(예: 모든 PR) | 내 CI 러너(예: GitHub Actions) | Claude API 키나 클라우드 제공업체 자격 증명이 있는 사람 |
| Copilot 코드 리뷰 | PR에서 Copilot을 리뷰어로 요청, 또는 자동 실행 설정 | GitHub | Copilot 이용 권한이 있는 사람(5단계 참고) |

<Aside type="caution" title="AI 리뷰는 사람을 대신하지 않아요">
관리형 Code Review는 댓글과 체크 실행을 남기고, 문서에 따르면 리뷰가 PR을 승인하거나 막지는 않아요. Copilot도 기본은 "Comment" 리뷰이고 "Approve"가 아니며, 승인은 관리자가 켜기 전에는 꺼져 있어요. AI 승인을 켤 수 있는 곳에서도 그것을 인정할지 의식적으로 정하세요. 중요한 변경은 동료가 직접 읽어요.
</Aside>

<Steps>

1. **내 컴퓨터 밖으로 나가도 되는 것 정하기**

   리뷰할 코드는 AI 서비스가 읽어요. 먼저 정리하세요. 이 저장소를 AI 도구와 써도 되는지 회사에 확인하세요([기초 5](/ko/basics/05-privacy-safety/), [기초 12](/ko/basics/12-privacy-settings/) 참고). 리뷰하기 전에 브랜치에서 API 키, 비밀번호, 개인정보를 빼고, 이미 커밋된 비밀 값은 새로 발급하세요. 공식 문서는 방법별로 이렇게 설명해요.

   - 관리형 Code Review는 Anthropic 인프라에서 돌고 Claude GitHub 앱으로 저장소에 접근해요. 리뷰 중에는 읽기 전용이고 커밋을 푸시하지 않아요.
   - 관리형 서비스는 Zero Data Retention이나 HIPAA 구성을 쓰는 조직에서는 쓸 수 없고, Anthropic의 Business Associate Agreement 대상도 아니에요.
   - `/code-review`는 내 세션에서 돌고, 사용량은 세션의 나머지처럼 플랜 한도나 API 요금에 들어가요.

   Copilot의 데이터 보관 방식은 하나하나 확인하지 못했어요. 내 플랜에 해당하는 내용은 GitHub 공식 페이지에서 확인하세요.

2. **Claude Code에서 `/code-review`로 첫 리뷰하기**

   저장소에서 리뷰할 브랜치로 `claude`를 열고 입력해요.

   ```text
   /code-review
   ```

   대상을 안 적으면, 문서에 따라 업스트림보다 앞선 브랜치의 커밋과 아직 커밋하지 않은 변경을 리뷰해요(업스트림이 없으면 `main`이나 이전 커밋과 비교해요). 리뷰는 자기 컨텍스트 창을 가진 백그라운드 서브에이전트로 돌고, 끝나면 결과가 대화에 도착해요. `/review`는 별칭이에요.

   다른 것을 리뷰하려면 대상을 붙여요.

   | 리뷰할 대상 | 입력 |
   | --- | --- |
   | 번호로 고른 풀 리퀘스트 | `/code-review 1234` |
   | 한 브랜치를 다른 브랜치와 비교 | `/code-review main...my-feature` |
   | 최근 커밋 15개 | `/code-review HEAD~15..HEAD` |
   | 파일이나 폴더 | `/code-review src/auth` |

   플래그 두 개가 다음 동작을 바꿔요. `--fix`는 Claude가 지적 사항을 작업 폴더에 직접 적용하게 하고, 그 수정은 권한 모드를 거쳐요. `--comment`는 지적을 GitHub 풀 리퀘스트에 인라인 댓글로(GitLab 머지 리퀘스트에는 노트 하나로) 올려요. 먼저 플래그 없이 실행해 결과를 읽어 보세요. 문서는 백그라운드 리뷰의 `--fix` 수정이 세션 체크포인트 밖에서 적용되어 `/rewind`로 되돌리지 못할 수 있다고 하니, 되돌릴 때는 git을 쓰세요.

   하나 더. 로컬 리뷰는 `CLAUDE.md`를 따르지만 `REVIEW.md`는 읽지 않아요. `REVIEW.md`는 관리형 서비스용 파일이에요.

3. **지적을 비판적으로 읽기**

   각 지적은 확인해야 할 단서예요. 파일과 줄을 열어 문제를 재현하거나 따져 보고 결정하세요. 이런 후속 프롬프트가 유용해요.

   <PromptBox>
   지적 2번에서 버그를 일으키는 입력과 문제가 생기는 줄을 정확히 보여 줘. 못 찾겠으면 못 찾았다고 말해 줘.
   </PromptBox>

   <PromptBox>
   이번 리뷰가 다루지 않은 부분(테스트, 설정, 자동 생성 파일)을 모두 알려 줘. 그건 내가 직접 읽을게.
   </PromptBox>

   목록이 길다고 좋은 리뷰는 아니에요. 문서는 관리형 서비스에 거짓 지적을 걸러 내는 검증 단계가 있다고 하지만, 그래도 놓칠 수 있다고 하니 깨끗한 결과가 증명은 아니에요.

4. **모든 풀 리퀘스트에 Claude 관리형 리뷰나 직접 만든 워크플로 쓰기**

   *관리형 Code Review.* Claude 조직의 Owner가 설정해요. GitHub에 있는 저장소를 쓰는 Team·Enterprise 플랜용이에요. 문서에 따르면 저장소마다 PR이 열릴 때 한 번, 푸시마다, 또는 요청할 때만 리뷰를 돌릴 수 있고, 쓰기 권한이 있는 사람은 `@claude review` 댓글로 시작할 수 있어요. 지적은 심각도 순 인라인 댓글로 달리고, "Claude Code Review"라는 체크 실행이 함께 생기며 이 체크는 실패로 끝나지 않아요. 리뷰 깊이는 Quick, Standard(기본), Deep 세 단계이고 깊을수록 비용이 더 들어요. 코드를 빌드하거나 실행하지 않아요. `REVIEW.md`는 기준 브랜치나 기본 브랜치에서 읽고, PR 자체의 변경에서는 읽지 않아요. 비용과 지출 한도는 공식 비용 페이지에 있는데 읽지 못했어요.

   *직접 만든 GitHub Actions 워크플로.* Claude Code에서 `/install-github-app`을 실행하면(github.com 저장소, 저장소 관리자 권한 필요) Claude GitHub 앱을 설치하고, 인증 비밀 값을 저장하고, 워크플로 파일을 추가하는 풀 리퀘스트를 열어 줘요. 문서의 리뷰 예제는 `code-review` 플러그인을 설치해 PR이 열리거나 갱신, 재오픈, 리뷰 준비 상태가 될 때 실행해요. 두 줄이 중요해요. 프롬프트의 `--comment`가 있어야 Claude가 PR에 올려요(없으면 지적은 워크플로 로그에만 남아요). 그리고 `claude_args`에는 인라인 댓글 도구를 지정한 `--allowedTools` 줄을 유지해야 해요.

   ```yaml
   # 공식 GitHub Actions 페이지에서 줄여 옮김. 전체 파일은 페이지를 확인하세요
   - uses: anthropics/claude-code-action@v1
     with:
       anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
       plugin_marketplaces: "https://github.com/anthropics/claude-plugins-official.git"
       plugins: "code-review@claude-plugins-official"
       prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
       claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'
   ```

   <Aside type="danger" title="키는 GitHub Secrets에 보관하세요">
   문서는 API 키나 OAuth 토큰을 절대 커밋하지 말라고 해요. GitHub Secrets에 저장하고 `${{ secrets.이름 }}`으로 참조하세요. 워크플로에는 필요한 권한만 주고, 병합 전에 Claude의 변경을 검토하세요. 이 워크플로는 GitHub Actions 분(minutes)과 API 토큰을 쓰므로 비용이 들어요. 공개 저장소에서는 포크에서 온 PR로 실행된 작업에 GitHub가 비밀 값을 주지 않아서, 같은 저장소 브랜치의 PR만 리뷰돼요.
   </Aside>

5. **GitHub에서 Copilot 리뷰 요청하기**

   GitHub.com에서 풀 리퀘스트를 열고, 오른쪽 사이드바의 **Reviewers**에서 Copilot 옆의 **Request**를 눌러요. 문서에 따르면 보통 30초 안에 끝나고, 각 댓글에 High·Medium·Low 심각도가 붙어요. 가능하면 두어 번 클릭으로 적용할 수 있는 수정 제안이 들어 있고, **Fix with Copilot**으로 클라우드 에이전트에게 수정을 맡길 수도 있어요(Copilot 코드 리뷰와 클라우드 에이전트가 켜져 있어야 해요).

   문서의 다른 사실이에요. 자동 리뷰 설정을 켜거나 재리뷰를 요청하지 않으면 새로 푸시한 내용은 다시 리뷰하지 않아요. 이미 해결한 댓글을 반복할 수도 있어요. VS Code에서는 PR을 열기 전에 선택한 코드나 커밋하지 않은 변경을 리뷰할 수 있어요. 노력 수준(Lite, Balanced, Max)은 철저함과 비용을 맞바꿔요. 페이지에 리뷰당 대략적인 평균 비용이 적혀 있지만 바뀔 수 있으니 의존하기 전에 확인하세요.

   Copilot을 안내하려면 `.github/copilot-instructions.md`(저장소 전체)나 `.github/instructions/**/*.instructions.md`(경로별)를 추가해요. 문서는 Copilot 코드 리뷰가 `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `REVIEW.md`가 있으면 그것도 읽고, 기준 브랜치가 아니라 내 변경이 있는 브랜치의 지침을 쓴다고 해요. 어떤 Copilot 플랜에 코드 리뷰가 포함되는지는 확인하지 못했어요. GitHub 플랜 페이지를 보세요.

6. **리뷰 안내를 쓰고, 마지막은 사람이 맡기**

   Claude 관리형 서비스는 기본적으로 서식이나 빠진 테스트가 아니라 정확성에 집중해요. 그 밖에 중요한 것은 읽는 파일에 적어 주세요. `REVIEW.md` 시작 예시예요.

   ```markdown
   # Review guidance
   - Flag any change that logs request bodies or tokens.
   - Database queries must use parameters, never string concatenation.
   - Skip style nits; our formatter handles them.
   ```

   병합 전에는 작성자가 받아들인 지적과 거절한 지적을 각각 설명하게 하고, 테스트를 직접 돌리고, 사람 리뷰어가 승인하게 하세요. AI와 사람의 의견이 다르면 사람이 결정해요.

</Steps>

## 자주 생기는 문제

### 리뷰에서 아무것도 안 나왔어요

- **원인**: 정말 없거나, 리뷰가 놓쳤을 수 있어요. 문서는 지적이 없어도 증명은 아니라고 해요.
- **해결**: 위험한 부분은 직접 읽고 테스트를 돌리세요.

### `--fix`가 예상 못 한 파일을 고쳤어요

- **원인**: `--fix`는 권한 모드를 거쳐 작업 폴더에 지적 사항을 적용해요.
- **해결**: `git diff`로 확인하고 필요하면 git으로 되돌리세요. 백그라운드 리뷰의 수정은 `/rewind`로 안 돌아올 수 있어요.

### 워크플로는 돌았는데 풀 리퀘스트에 아무것도 안 올라왔어요

- **원인**: `--comment`가 없으면 지적이 워크플로 실행 로그에만 남아요.
- **해결**: `--comment`와 위의 `--allowedTools` 줄을 추가하세요.

### Copilot이 새 커밋을 리뷰하지 않았어요

- **원인**: 새 푸시 자동 리뷰를 설정하지 않으면 Copilot은 다시 리뷰하지 않아요.
- **해결**: Reviewers 메뉴에서 Copilot 이름 옆의 재리뷰 버튼을 누르세요.

## 실전 팁

- 풀 리퀘스트는 작게 유지하세요. 사람이든 AI든 집중된 변경에서 더 많이 찾아요.
- 동료에게 부탁하기 전에 AI 리뷰를 먼저 돌려서, 사람은 설계와 의도에 시간을 쓰게 하세요.
- 지적을 이해하지 못한 채 그대로 고치지 마세요.
- 고객 데이터, 키, 비공개 문서가 든 코드는 리뷰용으로 보내지 마세요.
- 가격, 플랜 조건, 한도는 의존하기 전에 공식 페이지에서 다시 확인하세요. 바뀔 수 있어요.
