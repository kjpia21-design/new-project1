<Summary>
- 공식 문서의 풀 리퀘스트 흐름은 프롬프트 세 개예요. 변경 사항을 요약하게 하고, "create a pr"을 요청하고, PR 설명을 보강해 달라고 해요. 문서는 한 가지를 덧붙여요. Claude가 만든 PR은 제출 전에 직접 검토하고, 위험 요소를 짚어 달라고 하라는 거예요.
- Claude가 `gh pr create`(또는 `glab mr create`)로 PR을 만들면 Claude Code가 세션을 그 PR에 연결해요. 나중에 `claude --from-pr 1234`(내 PR 번호)로 그 PR에 연결된 세션을 다시 열 수 있어요.
- 브랜치별로 병렬 작업을 하려면 `claude --worktree feature-auth`가 세션마다 별도 체크아웃과 브랜치를 줘요. 저장소에 커밋이 최소 하나는 있어야 해요.
- 되돌리기는 두 겹이에요. `/rewind`(또는 빈 프롬프트에서 `Esc` 두 번)는 Claude가 자체 도구로 고친 파일을 되돌려요. 하지만 체크포인트 페이지는 Bash 명령으로만 바뀐 변경은 추적하지 않는다고 하고, 그런 변경과 영구 이력은 Git을 쓰라고 해요.
- 모범 사례 페이지에는 푸시 전에 항상 묻게 하는 규칙이 나와요. `.claude/settings.json`의 `"ask": ["Bash(git push *)"]`예요.
- 2026-11-02에 공식 페이지 세 곳을 읽었어요. 이 튜토리얼을 위해 Claude Code를 직접 실행해 보지는 않았어요. Git 명령은 일반적인 Git 사용법이고, 프롬프트와 커밋 메시지 조언은 우리가 만든 거예요.
</Summary>

## 이 튜토리얼로 할 수 있게 되는 것

- Claude에게 변경 사항을 보게 하고 알아보기 쉬운 커밋 메시지 초안을 받은 뒤, 읽어 보고 나서 커밋해요.
- 별도 브랜치에서 작업해 `main`을 안전하게 지켜요.
- 무엇이 왜 바뀌었고 어떻게 테스트했는지 담은 PR 설명을 받아요.
- `/rewind`나 Git으로 잘못된 변경을 되돌리고, 푸시 전에 diff를 확인해요.

## 먼저 알아둘 개념

**커밋**은 변경 사항을 메시지와 함께 저장한 스냅샷이에요. **브랜치**는 별도의 작업 줄기라서 실험이 `main`을 건드리지 않아요. **풀 리퀘스트(PR)**는 내 브랜치를 다른 브랜치에 합쳐 달라는 요청이고, 다른 사람이 리뷰할 수 있는 페이지가 생겨요. **diff**는 바뀐 줄의 목록이에요. [1. Claude Code 시작하기](/ko/coding/06-claude-code-start/)에서 시작 방법을, [13편](/ko/coding/40-settings-permissions/)에서 allow·ask·deny 규칙을, [15편](/ko/coding/42-code-review-ai/)에서 변경 리뷰를 볼 수 있어요. 클라우드에서 GitHub 작업을 맡기는 방법은 [3편](/ko/coding/08-cloud-github/), 자동 검사는 [10편](/ko/coding/37-claude-code-hooks/)을 참고하세요.

<Aside type="caution" title="푸시는 완전히 되돌리기 어려운 단계예요">
내 컴퓨터의 커밋과 브랜치는 되돌리기 쉬워요. 푸시는 작업을 공유하는 일이고, 강제 푸시는 다른 사람의 작업을 덮어쓸 수 있어요. `.env` 같은 비밀 파일은 커밋에 넣지 말고, diff를 먼저 읽고, 푸시 시점은 내가 정하세요. 모범 사례 페이지는 자동 모드가 다른 사람의 작업을 덮어쓰는 강제 푸시 같은 일을 이미 막는다고 하고, 내가 정한 "절대 안 돼" 규칙은 deny 규칙이나 훅에 두라고 해요.
</Aside>

## 단계별 따라 하기

<Checklist items={[
  '연습용 저장소이거나 별도 브랜치에서 작업 중이다 (main에 직접 하지 않는다)',
  '커밋 전에 git status와 git diff를 내가 직접 실행했다',
  '커밋 메시지를 읽었고 실제 변경과 맞는다',
  '커밋에 비밀 값이나 생성된 파일이 들어 있지 않다',
  'PR 설명을 읽고 나서 열었고, 푸시 시점은 내가 정한다',
]} />

<Steps>

1. **브랜치에서 시작하기**

   Claude에게 수정을 시키기 전에 작업용 브랜치를 만드세요. 내 터미널에서 해요.

   ```bash
   git switch -c fix-login-redirect
   git status
   ```

   브랜치 이름은 자유예요. 나중에 찾기 쉽게 짧은 설명이 좋아요. 작업 두 개를 동시에 하려면 common-workflows 페이지의 worktree를 쓸 수 있어요. `claude --worktree feature-auth`는 별도 체크아웃과 브랜치에서 세션을 시작하고, 다른 터미널에서 다른 이름으로 실행하면 또 하나가 시작돼요. 저장소에 커밋이 최소 하나는 있어야 하고, 커밋이 없으면 `Failed to resolve base branch "HEAD"` 오류로 실패한다고 해요. 정리 방법은 Worktrees 페이지에 있다고 하는데, 그 페이지는 읽지 않았어요.

2. **푸시 안전 규칙 정하기 (선택)**

   모범 사례 페이지의 권한 예시에는 `Bash(git push *)`가 `ask` 목록에 들어 있어서, 푸시 전에 Claude가 항상 물어봐요. `Read(./.env)` 같은 `deny` 항목으로 비밀 파일을 Claude에게서 숨기는 예시도 있어요. 규칙은 [13편](/ko/coding/40-settings-permissions/)에서 설명한 대로 `.claude/settings.json`에 둬요.

   ```json
   {
     "permissions": {
       "ask": ["Bash(git push *)"],
       "deny": ["Read(./.env)", "Read(./secrets/**)"]
     }
   }
   ```

   규칙은 의도가 아니라 도구 호출에 맞춰지므로 보호 장치 중 한 겹으로만 보고, 한계는 페이지에서 확인하세요.

3. **작게 고치게 하고, 내가 직접 보기**

   아래 같은 프롬프트로 작고 분명한 변경 하나를 부탁하세요. 그다음 커밋 전에 내 터미널에서 무엇이 바뀌었는지 확인해요.

   ```bash
   git status   # 바뀌었거나 새로 생긴 파일
   git diff     # 바뀐 모든 줄
   ```

   로그, 빌드 결과물, `.env`처럼 예상하지 못한 파일이 없는지 살펴보세요.

4. **커밋 메시지를 받고 커밋하기**

   Claude는 diff를 읽고 메시지 초안을 쓸 수 있어요. 먼저 내가 검토하는 방식을 추천해요.

   <PromptBox>
   지금 변경 사항을 git diff로 확인해 줘. 커밋 메시지 초안을 써 줘. 첫 줄은 50자 이내로 무엇을 했는지 명령형으로 쓰고, 그 아래에 왜 필요했는지 짧게 적어 줘. 아직 커밋하지 마. 메시지를 보여 주고, 관련 없어 보이는 파일이 있으면 알려 줘.
   </PromptBox>

   메시지가 정확하면 직접 커밋하거나(`git add <파일>` 후 `git commit -m "..."`), Claude에게 "이 파일들만 그 메시지로 커밋해"라고 하세요. 50자 첫 줄과 명령형은 Git에서 흔히 쓰는 관례이고 Claude Code 문서의 규칙은 아니에요. 전부 스테이징하지 말고 파일을 지정해서, 관련 없는 변경이 섞이지 않게 하세요.

5. **커밋은 작게, 따로따로**

   아이디어 하나에 커밋 하나면 이력이 읽기 쉽고 되돌리기도 쉬워요. 변경이 두 가지 섞여 있으면 이렇게 물어보세요.

   <PromptBox>
   작업 폴더에 버그 수정과 서식 정리, 두 종류의 변경이 섞여 있어. 두 커밋으로 나누는 방법, 각 커밋에 들어갈 파일, 각각의 메시지를 제안해 줘. 내가 동의하기 전에는 git 명령을 실행하지 마.
   </PromptBox>

6. **풀 리퀘스트 작성하기**

   공식 페이지는 직접 요청("create a pr for my changes")하거나 단계별로 하라고 해요. 변경 사항을 요약하게 하고, "create a pr"을 실행하고, "enhance the PR description with more context about the security improvements"처럼 다듬는 거예요. PR을 만들려면 원격 저장소가 필요하고, 우리가 이해한 바로는 `gh` 도구에 로그인되어 있어야 해요. 모범 사례 페이지는 `gh`가 설치되고 로그인되어 있으면 Claude가 설명 없이도 PR을 열고 리뷰 댓글을 읽는다고 해요. 다른 환경은 확인하지 못했어요. 먼저 쓸 프롬프트예요.

   <PromptBox>
   이 브랜치가 main과 비교해 무엇이 바뀌었는지 쉬운 말로 요약해 줘. 그다음 PR 설명 초안을 써 줘. 항목은 변경 내용, 이유, 내가 테스트한 방법, 위험 요소, 리뷰어가 확인할 점이야. 보여 주기만 하고 아직 PR은 열지 마. 테스트하지 않은 것이 있으면 했다고 쓰지 말고 안 했다고 적어 줘.
   </PromptBox>

   설명이 맞으면 Claude에게 PR을 열게 하거나 `gh pr create`를 직접 실행하세요. 페이지는 생성된 PR을 제출 전에 검토하고, 잠재적 위험과 고려할 점을 짚어 달라고 하라고 해요.

7. **의도해서 푸시하고, 리뷰하기**

   푸시는 내 브랜치를 원격에 보내는 일이에요. 2단계의 `ask` 규칙이 있으면 Claude가 먼저 물어봐요. 확신이 없으면 `git push -u origin <브랜치>`로 직접 푸시하세요. PR이 생기면 `/code-review`로 대화를 보지 못한 새 서브에이전트의 리뷰를 받고([15편](/ko/coding/42-code-review-ai/) 참고), 리뷰어가 볼 PR 페이지를 나도 읽어 보세요.

8. **잘못된 것 되돌리기**

   피해에 맞는 방법을 고르세요.

   | 상황 | 사용할 것 |
   | --- | --- |
   | 이 세션에서 Claude가 엉뚱한 쪽으로 가고 있다 | `Esc`로 멈추기. 그때까지의 작업은 유지돼요 |
   | 이 세션에서 Claude가 고친 파일이 잘못됐다 | `/rewind` 또는 빈 프롬프트에서 `Esc` 두 번으로 코드·대화·둘 다 되돌리기 |
   | Bash 명령으로만 바뀐 파일이다 | `/rewind`는 추적하지 않음. Git 사용 (`git restore <파일>`) |
   | 마지막 커밋의 메시지나 내용이 틀렸고 푸시 전이다 | `git commit --amend` (일반 Git) |
   | 이미 푸시했거나 공유한 커밋이다 | 공유된 이력을 고쳐 쓰지 말고 `git revert`(일반 Git)로 되돌리는 새 커밋 추가 |

   체크포인트 페이지는 체크포인트가 빠른 세션 단위 복구용이고, 커밋·브랜치·장기 이력은 계속 Git을 쓰라고 해요. 되감기는 내 커밋을 대신하지 않아요.

</Steps>

## 자주 겪는 문제

### 의도하지 않은 파일이 커밋에 들어갔어요

- **원인**: 전부 한꺼번에 스테이징했어요.
- **해결**: 커밋 전에 `git status`를 보고 파일을 지정해서 스테이징하세요. 스테이징에서 빼려면 `git restore --staged <파일>`을 쓰세요.

### 커밋 메시지가 실제 변경보다 거창해요

- **원인**: 실제 diff가 아니라 목표를 보고 메시지를 썼어요.
- **해결**: `git diff`만 근거로 메시지를 쓰게 하고, 내가 직접 고치세요.

### Claude가 PR을 만들지 못했어요

- **원인**: 원격 저장소가 없거나, `gh`에 로그인되어 있지 않거나, 아직 푸시하지 않았을 수 있어요. 정확한 오류 메시지는 확인하지 못했어요.
- **해결**: `git remote -v`와 `gh auth status`를 직접 확인하고, 브랜치를 푸시한 뒤 다시 요청하세요.

### /rewind로 변경이 되돌아가지 않았어요

- **원인**: Bash 명령으로만 바뀐 파일이라 체크포인트가 추적하지 않아요.
- **해결**: Git을 쓰세요. `git restore <파일>` 또는 깨끗한 브랜치로 `git switch` 하세요.

## 실전 팁

- 먼저 버려도 되는 저장소에서 연습하고 실제 작업으로 넘어가세요.
- 큰 작업을 Claude에게 맡기기 전에 커밋해 두면 돌아갈 깨끗한 지점이 생겨요.
- diff는 항상 직접 읽으세요. 그럴듯한 커밋 메시지가 엉뚱한 변경을 설명할 수도 있어요.
- 비밀 값은 절대 커밋하지 마세요. 이미 커밋하거나 푸시했다면 노출된 것으로 보고 교체하세요.
- Claude Code는 자주 바뀌니 명령은 공식 페이지에서 다시 확인하세요.
