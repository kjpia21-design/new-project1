## 이 튜토리얼로 할 수 있게 되는 것

- 오류를 Claude에게 가장 도움이 되는 형태로 전달해요. 오류 문구, 오류를 일으키는 명령, 기대하는 결과예요.
- 오류 메시지나 로그를 공유하기 전에 비밀 정보를 가려요.
- "먼저 설명만"(계획 모드)과 "바로 수정" 중에서 고르고, 되돌리는 방법(`Esc`, `/rewind`, git)을 알아요.
- 수정 전에는 실패하고 수정 후에는 통과하는 테스트로 고쳐졌는지 확인하고, diff를 검토해요.

## 먼저 알아둘 개념

**스택 트레이스**는 프로그램이 멈출 때 출력되는 함수 호출 목록이에요. 윗부분이 실패한 파일과 줄을 가리키는 경우가 많아요. **회귀 테스트**는 버그 때문에 실패하고, 고친 뒤로는 계속 통과해야 하는 테스트예요. [1. Claude Code 시작하기](/ko/coding/06-claude-code-start/)에서 시작 방법을, [13편](/ko/coding/40-settings-permissions/)에서 아래에 쓰는 권한 모드와 deny 규칙을, [15편](/ko/coding/42-code-review-ai/)에서 병합 전 리뷰 방법을 볼 수 있어요.

<Aside type="caution" title="오류에 비밀 정보가 섞일 수 있어요">
로그와 스택 트레이스에는 API 키, 토큰, 비밀번호, 접속 문자열, 고객 이름, 이메일이 들어 있기도 해요. 붙여 넣은 내용은 AI 서비스로 전달돼요. 먼저 `REDACTED` 같은 표시로 바꾸고, 진짜 비밀 값이 이미 공유됐다면 새 값으로 교체하세요. [기초 5편](/ko/basics/05-privacy-safety/)과 [기초 12편](/ko/basics/12-privacy-settings/)을 참고하세요.
</Aside>

## 단계별 따라 하기

<Checklist items={[
  '명령 하나로 오류를 재현할 수 있다',
  '공유할 내용에서 키, 토큰, 개인정보를 지웠다',
  'Claude에게 "고쳐졌다"의 기준을 알려 주고 실행할 테스트나 명령을 줬다',
  '제안된 원인과 diff를 읽고 나서 수락했다',
  '테스트를 내가 직접 돌렸고 되돌리는 방법(git)을 안다',
]} />

<Steps>

1. **오류를 재현하고 상황을 적어 두기**

   실패하는 정확한 명령(예: `npm test`), 오류 전문, 항상 나는지 가끔 나는지를 적어 두세요. 공식 팁은 오류를 재현하는 명령과 스택 트레이스를 알려 주고, 재현 단계를 적고, 간헐적인지 일관적인지 알려 주라고 해요. 되돌릴 수 있도록 Git 저장소의 별도 브랜치에서 작업하세요.

2. **공유하기 전에 메시지 정리하기**

   오류 문구를 메모 파일에 복사해 놓고 비공개 정보를 바꾸세요. 키, 토큰, 비밀번호, 자격 증명이 든 URL, 사용자 이름, 이메일 같은 것들이에요. 오류 종류, 메시지, 파일 이름, 줄 번호처럼 중요한 부분은 남겨요. `.env` 전체나 로그 전체를 붙이지 말고 관련된 줄만 붙이세요.

   Claude가 비밀 파일을 아예 못 보게 할 수도 있어요. 모범 사례 페이지는 `.claude/settings.json`의 `permissions.deny`에 `Read(./.env)`, `Read(./.env.local)`, `Read(./secrets/**)` 같은 항목을 두는 예를 보여 주고, 이렇게 하면 Claude에게 `.env`의 내용을 물어도 Read 도구로든 `cat .env`로든 실패한다고 해요. 규칙은 의도가 아니라 도구 호출을 기준으로 맞춰지므로 한계가 있다고도 하니, 한 겹의 보호로 생각하고 해당 페이지를 읽어 보세요. 규칙이 놓이는 위치는 [13편](/ko/coding/40-settings-permissions/)에서 설명해요.

3. **Claude Code를 열고 맥락과 함께 오류 공유하기**

   프로젝트 폴더에서 `claude`를 여세요. 문서의 시작 예시는 "I'm seeing an error when I run npm test"처럼 짧아요. 더 구체적으로 쓰면 낫습니다. 모범 사례 페이지는 파일 이름, 증상, "고쳐졌다"의 기준을 적으면 보통 수정 한 번을 아낄 수 있다고 해요. 아래는 우리가 만든 프롬프트 템플릿이에요.

   <PromptBox>
   npm test를 돌리면 "saves a draft" 테스트가 실패해요. 정리한 오류는 아래에 있어요. 이 테스트가 통과해야 해요. 먼저 가장 가능성 높은 원인을 쉬운 말로 설명하고 파일과 줄을 알려 주세요. 아직 파일은 바꾸지 마세요.

   TypeError: Cannot read properties of undefined (reading 'id') at saveDraft (src/drafts.js:42)
   </PromptBox>

   모범 사례 페이지에 나온 다른 전달 방법도 있어요. `@`와 경로를 입력하면 파일 내용이 포함돼요. 오류 스크린샷을 프롬프트에 붙여 넣을 수 있어요(common-workflows 페이지는 이미지를 끌어다 놓거나 `Ctrl+V`로 붙여 넣는 방법을 안내해요). 명령 출력을 `cat error.log | claude -p "what's going on here"`처럼 파이프로 넘길 수도 있어요. 로그를 넘길 때는 먼저 정리하세요.

4. **수정 전에 원인부터 묻기**

   좋은 디버깅은 증상과 원인을 나눠요. 여러 가설과 구별하는 방법을 물어보세요.

   <PromptBox>
   이 오류의 가능성 높은 원인 세 가지를 코드에서 찾은 근거와 함께 알려 주세요. 각각을 확인하거나 배제할 명령이나 로그 한 줄도 알려 주세요. 그다음 제가 고를 때까지 기다려 주세요.
   </PromptBox>

   파일이 수정되기 전에 계획을 검토하고 싶다면 문서의 **계획 모드(plan mode)**를 쓰세요. Claude가 파일을 읽고 계획을 제안하지만 승인하기 전에는 수정하지 않고, 상태 표시줄에 "plan mode on"이 보여요. `claude --permission-mode plan`으로 시작해요. common-workflows 페이지의 두 번째 단계도 같은 생각이에요. 수정 방법을 몇 가지 물어보고(예시: "suggest a few ways to fix the @ts-ignore in user.ts") 하나를 적용해요.

5. **실패하는 테스트를 먼저, 그다음 작은 수정**

   모범 사례 페이지의 예시 프롬프트는 관련 코드를 보고, 문제를 재현하는 실패 테스트를 쓰고, 그다음 고치라는 순서예요. 올바른 이유로 실패하는 테스트는 버그를 찾았다는 증거이고, 같은 테스트가 버그의 재발도 막아 줘요.

   <PromptBox>
   이 실패를 재현하는 테스트를 쓰고, 실행해서 이 오류로 실패하는 것을 보여 주세요. 그다음 원인을 고치는 가장 작은 변경만 하세요. try/catch로 덮거나, 나쁜 데이터를 가리는 기본값을 넣거나, 테스트를 건너뛰는 식으로 오류를 숨기지 마세요. 테스트를 다시 돌리고 출력을 보여 주세요.
   </PromptBox>

   "오류를 숨기지 마세요"는 우리의 조언이에요. AI가 원인은 그대로 두고 오류 메시지만 없애 버릴 수 있으니, 조용한 화면이 아니라 원인을 요구하세요. 제안되는 수정은 수락하기 전에 읽어 보세요. Claude가 작업 중에 엉뚱한 방향으로 가면 `Esc`로 멈출 수 있고, 그때까지의 작업은 그대로 남아요.

6. **직접 확인하기**

   문서는 Claude가 작업이 끝난 것처럼 보이면 멈춘다고 하고, 통과·실패로 답이 나오는 확인 수단이 있으면 Claude가 변경하고, 실행하고, 출력을 읽고, 깨진 부분을 고치는 루프를 스스로 닫을 수 있다고 해요. 또 증거, 즉 실행한 명령과 그 출력을 요청하라고 해요. "모든 테스트 통과"라는 말만으로는 알 수 있는 게 적기 때문이에요. 그리고 내 확인도 하세요.

   ```bash
   # Claude를 거치지 말고 내 터미널에서 실행하세요
   git diff            # 바뀐 줄을 모두 읽기
   npm test            # 또는 프로젝트의 테스트 명령
   ```

   새 테스트가 수정 없이는 실패하고 수정하면 통과하는지 확인하세요(수정을 잠시 되돌려 실패하는지 볼 수 있어요). 부작용을 잡으려면 새 테스트만이 아니라 전체 테스트를 돌리세요. 실제 동작이 중요하면 앱을 실행해 처음의 재현 단계를 다시 해 보세요.

7. **수정이 잘못되면 깔끔하게 되돌리기**

   Claude가 딴 길로 가면 모범 사례 페이지는 바로 `Esc`를 누르고, 두 번 고쳐도 안 되면 세 번째 수정 대신 `/clear` 후 더 나은 프롬프트를 쓰라고 해요. `/rewind`(또는 빈 프롬프트에서 `Esc` 두 번)는 코드, 대화, 또는 둘 다를 이전 프롬프트 시점으로 되돌리는 메뉴를 열어요. git도 여전히 안전망이에요. `git restore <파일>`이나 깨끗한 브랜치로 `git switch` 하세요.

   내가 쓰지 않은 코드의 어려운 버그라면, 모범 사례 페이지는 `/effort high`나 `/effort xhigh`로 노력 수준을 올리면 Claude가 더 많은 경계 사례를 확인하지만 시간과 토큰이 더 든다고 해요.

8. **리뷰를 받고 원인을 기록하기**

   테스트가 통과하면 `/code-review`가 내 대화를 보지 못한 새 서브에이전트로 변경을 검토해 줘요([15편](/ko/coding/42-code-review-ai/) 참고). 그다음 커밋 메시지나 티켓에 쓸 짧은 메모를 요청하세요.

   <PromptBox>
   다섯 줄로 요약해 주세요. 증상, 근본 원인, 우리가 한 변경, 테스트 방법, 다음에 주의할 점 하나예요. 실행하지 않은 것은 했다고 쓰지 마세요.
   </PromptBox>

</Steps>

| 로그를 파이프로 전달 (먼저 정리) | `cat error.log \| claude -p "what's going on here"` |
| 파일 포함하기 | `@`와 경로 입력 |

## 자주 겪는 문제

### 오류 메시지만 사라지고 버그는 그대로예요

- **원인**: 원인을 고친 게 아니라 증상을 가렸을 수 있어요(예외 삼키기, 기본값 넣기).
- **해결**: 근거와 함께 근본 원인을 묻고, 수정 전에는 실패하고 수정 후에는 통과하는 테스트를 요구하세요.

### Claude가 오류를 재현하지 못해요

- **원인**: 명령, 입력, 환경, 간헐적인지 여부 같은 정보가 빠졌어요.
- **해결**: 정확한 명령과 단계, 항상 나는지 여부를 알려 주세요. 가끔 나는 버그면 그렇다고 말하고 무엇이 달라지는지 찾게 하세요.

### 고쳤더니 다른 곳이 깨져요

- **원인**: 공용 코드를 건드렸는데 새 테스트만 돌렸어요.
- **해결**: 전체 테스트를 돌리고 `git diff`를 읽고, 필요하면 git으로 되돌리세요.

### 비밀 값을 실수로 붙여 넣었어요

- **원인**: 로그나 오류에 키나 토큰이 들어 있었어요.
- **해결**: 노출된 것으로 보고 발급한 서비스에서 교체하세요. 다음 메시지는 정리한 뒤 공유하세요.

## 실전 팁

- 한 번에 하나만 바꾸고, 바꿀 때마다 테스트를 다시 돌리세요.
- 앱 전체보다 작은 재현 예시가 디버깅하기 쉬워요. 실패하는 경우를 줄이도록 Claude에게 도움을 청하세요.
- 실제 오류 문구를 프롬프트에 그대로 넣으세요. "죽어요" 같은 요약은 단서를 잃어요.
