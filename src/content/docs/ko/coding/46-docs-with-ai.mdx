- 팁은 이래요. 원하는 문서 스타일(JSDoc, docstring 등)을 지정하고, 예시를 요청하고, 공개 API·인터페이스·복잡한 로직의 문서를 요청해요.
- 모범 사례 페이지는 Claude에게 증거, 즉 실행한 명령과 출력을 달라고 하라고 해요. "All tests pass"라는 말만으로는 알 수 있는 게 거의 없다는 이유예요. 같은 생각을 문서에도 적용해, 문서의 각 주장 뒤에 있는 명령과 출력을 달라고 해요.
- 같은 페이지에 `Read(./.env)` 같은 `deny` 권한 규칙 예시가 있고, 이 규칙은 모든 권한 모드에서 적용된다고 해요. 문서를 쓰는 동안 비밀 파일을 Claude에게서 떨어뜨리는 방법 하나로 소개해요.
- 2026-11-05에 공식 페이지 두 곳을 읽었어요. 이 튜토리얼을 위해 Claude Code를 직접 실행해 보지는 않았어요. 프롬프트와 확인 절차는 우리 조언이고 공식 규칙이 아니에요.
</Summary>

## 이 튜토리얼로 할 수 있게 되는 것

- 실제 프로젝트를 바탕으로 Claude에게 README나 코드 주석 초안을 받아요.
- 문서의 각 문장(설치 방법, 명령, 옵션)을 믿지 않고 코드와 대조해 확인해요.
- 비밀번호, 키, 개인정보가 문서와 대화에 들어가지 않게 해요.
- 결과를 diff로 검토하고 커밋해요.

## 먼저 알아둘 개념

**AI가 쓴 문서는 그럴듯해도 틀릴 수 있어요.** 프로젝트가 다른 명령을 쓰는데 README에 `npm run build`라고 적혀 있으면, 누군가 따라 하기 전까지는 멀쩡해 보여요. 그래서 이 튜토리얼의 핵심은 쓰기보다 확인이에요. [1. Claude Code 시작하기](/ko/coding/06-claude-code-start/)에서 시작 방법을 볼 수 있어요. 커밋 전에 변경을 리뷰받으려면 [15편](/ko/coding/42-code-review-ai/), 브랜치·커밋 습관은 [17편](/ko/coding/44-git-with-claude-code/)을 참고하세요. "Claude에게 확인 수단을 준다"는 생각은 [18편](/ko/coding/45-refactoring-with-ai/)에서도 써요.

<Aside type="caution" title="문서와 프롬프트에 비밀 정보를 넣지 마세요">
README에는 채워야 할 설정이 자주 나와요. 이름(예: `DATABASE_URL`)과 가짜 예시 값만 적고, 진짜 값은 절대 적지 마세요. 실제 비밀번호, API 키, 고객 데이터를 프롬프트에 붙여 넣지 말고, 커밋하기 전에 diff에서 확인하세요.
</Aside>

## 단계별 따라 하기

<Steps>

1. **안전한 환경 준비하기**

   내 터미널에서 브랜치를 만들어 두면 문서 변경을 검토하거나 버리기 쉬워요.

   ```bash
   git switch -c docs-readme
   git status
   ```

   실제 비밀 정보가 든 파일이 커밋되어 있거나 Claude가 읽을 위치에 있지 않은지 확인하세요. 모범 사례 페이지는 `.claude/settings.json`의 deny 규칙으로 그런 파일 읽기를 막는 예시를 보여 줘요.

   ```json
   {
     "permissions": {
       "deny": ["Read(./.env)", "Read(./.env.local)", "Read(./secrets/**)"]
     }
   }
   ```

   페이지에 따르면 deny 규칙은 모든 권한 모드에서 적용되고, 이렇게 저장하면 Claude에게 `.env` 내용을 물어도 실패해요. 경로는 내 프로젝트에 맞게 바꾸세요. 이 파일은 여기서 직접 시험하지 않았어요.

2. **문서가 없는 곳 찾기**

   공식 레시피는 수정이 아니라 질문으로 시작해요. 읽기만 하는 프롬프트를 써 보세요.

   <PromptBox>
   이 프로젝트를 살펴봐 줘. 아무것도 수정하지 마. 주석이나 문서가 없는 파일과 함수를 나열하고, 그중 공개된 것(다른 코드나 사용자가 쓰는 것)을 표시해 줘. 기존 README에 빠진 것도 알려 줘. 설치, 실행, 테스트 방법 같은 거야.
   </PromptBox>

3. **README 초안 쓰기**

   팁이 원하는 스타일을 지정하라고 하니, 스타일과 독자를 알려 주세요.

   <PromptBox>
   이 프로젝트의 README.md 초안을 새로 들어온 개발자를 위해 써 줘. 프로젝트가 하는 일, 요구 사항, 설치, 실행, 테스트 실행 방법, 주요 폴더를 넣어 줘. 모든 명령은 이 저장소의 파일을 근거로 하고, 파일에서 가져온 명령마다 옆에 파일 이름을 적어 줘. 확실하지 않은 부분은 추측하지 말고 TODO라고 적어 줘. 설정 값에는 가짜 예시 값을 써 줘.
   </PromptBox>

   명령마다 출처를 달라고 하고 빈 곳은 `TODO`로 두게 하면 다음 단계가 쉬워져요.

4. **중요한 부분에 코드 문서 달기**

   레시피의 예시는 `add JSDoc comments to the undocumented functions in auth.js`예요. 내 언어의 스타일에 맞게 쓰세요.

   <PromptBox>
   auth.js의 공개 함수에 이 프로젝트가 이미 쓰는 스타일(JSDoc, docstring 등)로 문서 주석을 달아 줘. 각 함수가 하는 일, 매개변수, 반환값, 짧은 예시 하나를 적어 줘. 코드는 바꾸지 말고 주석만 추가해. 코드에서 보이지 않는 동작은 설명하지 마.
   </PromptBox>

   팁은 공개 API·인터페이스·복잡한 로직의 문서를 요청하고, 예시를 넣어 달라고도 해요.

5. **모든 주장 확인하기**

   이 단계는 모범 사례 페이지의 "증거를 요청하라"는 조언을 적용한 우리 방식이에요. 초안을 훑으면서 내 터미널에서 할 수 있는 것은 직접 시험하세요.

   | 문서의 내용 | 확인 방법 |
   | --- | --- |
   | 설치·실행 명령 | 깨끗한 복사본에서 실행하거나 "실행 안 함"으로 표시 |
   | 테스트 명령 | 실행해서 결과 비교 |
   | 설정·환경 변수 | 코드에서 이름을 검색해 실제로 쓰이는지 확인 |
   | 폴더 설명 | `ls` 결과와 비교 |
   | 함수 설명 | 함수와 예시 호출을 직접 읽기 |

   Claude에게 1차 점검을 맡기고, 그 보고를 내가 다시 확인해도 돼요.

   <PromptBox>
   README를 코드와 대조해 줘. README에 나온 명령과 설정마다 실행하거나 검색하고, 실행한 명령과 출력을 보여 줘. 맞지 않는 것을 모두 나열하되, 아직 고치지는 마.
   </PromptBox>

   내가 직접 실행하는 단계를 건너뛰지 마세요. Claude의 보고는 단서이지 증명이 아니에요.

6. **다듬고 기준에 맞추기**

   레시피의 마지막 두 단계는 맥락과 예시를 더해 다듬고, 프로젝트 표준에 맞는지 확인하는 거예요. 스타일 가이드가 있으면 알려 주세요.

   <PromptBox>
   찾은 불일치를 반영해 README를 다듬어 줘. 핵심 사용 사례의 예시를 하나 넣어 줘. 그다음 우리 문서 스타일에 맞는지 확인해 줘. 스타일은 짧은 문장, 명령은 코드 블록, 홍보 문구 금지야. 무엇을 바꿨는지 알려 줘.
   </PromptBox>

7. **diff를 읽고 커밋하기**

   ```bash
   git diff      # 바뀐 모든 줄
   git status    # 예상하지 못한 파일
   ```

   실제 키, 내부 주소, 이름이나 이메일 주소가 있는지, 주석만 부탁했는데 코드가 바뀌지 않았는지 보세요. 괜찮으면 커밋해요.

   ```bash
   git add README.md auth.js
   git commit -m "Add README and doc comments"
   ```

   파일 이름은 내 것으로 바꾸세요. 한 번 더 확인받고 싶으면, 모범 사례 페이지에 따르면 `/code-review`가 새 서브에이전트에서 diff를 리뷰해요.

</Steps>

## 빠른 참고

| 할 일 | 위치 또는 방법 |
| --- | --- |
| 문서 없는 코드 찾기 | 읽기 전용 프롬프트, "아무것도 수정하지 마" |
| 스타일 정하기 | 프롬프트에 JSDoc, docstring 등을 적기 |
| 증거 요청 | "실행한 명령과 출력을 보여 줘" |
| 비밀 파일 막기 | `.claude/settings.json`의 `deny` 규칙 |
| diff 검토 | `git diff` 또는 `/code-review` |
| 코드 변경 없이 문서만 | "주석만, 코드는 바꾸지 마"라고 쓰기 |

## 자주 겪는 문제

### README에 없는 명령이 적혀 있어요

- **원인**: Claude가 내 파일을 읽지 않고 흔한 관례로 추측했어요.
- **해결**: 명령마다 근거 파일을 적게 하고, 추측은 `TODO`로 바꾸게 한 다음 명령을 직접 실행해 보세요.

### 주석이 코드가 하지 않는 일을 설명해요

- **원인**: 함수 이름만 보고 썼고 본문은 반영하지 않았어요.
- **해결**: 코드에서 보이는 것만 설명하라고 하세요. 주석 옆의 함수를 직접 읽어 보세요.

### 주석만 부탁했는데 코드가 바뀌었어요

- **원인**: 프롬프트가 코드 수정을 금지하지 않았어요.
- **해결**: `git diff`를 확인하고 `git restore <파일>`로 되돌린 뒤 "주석만"이라고 다시 요청하세요.

### 문서에 실제 키나 주소가 들어갔어요

- **원인**: Claude가 읽은 파일에서 그대로 가져왔어요.
- **해결**: 커밋하기 전에 지우세요. 이미 커밋하거나 푸시했다면 노출된 것으로 보고, 해당 서비스의 안내에 따라 새 키로 교체하세요.

### 문서가 금방 낡아요

- **원인**: 문서를 쓴 뒤 코드가 바뀌었어요.
- **해결**: 명령이나 설정이 바뀔 때마다 5단계 확인을 다시 하세요. 우리 제안은 이것을 풀 리퀘스트 체크리스트에 넣는 거예요.

## 실전 팁

- 먼저 버려도 되는 프로젝트에서 연습하세요.
- 추측 대신 `TODO`를 쓰게 하세요.
- 문서에는 가짜 예시 값을 쓰고, 진짜 값은 절대 쓰지 마세요.
- 문서 변경은 별도 커밋으로 두면 검토하기 쉬워요.
- Claude Code는 자주 바뀌니 명령은 공식 페이지에서 다시 확인하세요.
