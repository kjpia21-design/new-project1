<Summary>
- 오류는 최상위 `error` 객체(`type`, `message`)와 `request_id`가 든 JSON으로 와요. `request-id` 응답 헤더를 로그에 남기세요. 지원팀에 문의할 때 필요해요.
- 문서에 있는 코드: 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 409 `conflict_error`, 413 `request_too_large`, 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error`예요.
- 공식 SDK는 일시적 실패를 지수 백오프로 **기본 2번** 다시 시도하고, `retry-after`가 있으면 따라요. `max_retries`로 바꾸거나 끌 수 있어요. Python SDK 페이지는 연결 오류, 408, 409, 429, 5xx를 재시도한다고 적어요.
- 429는 `retry-after` 초만큼 기다리세요. 그보다 일찍 재시도하면 실패해요. 모든 429에 이 헤더가 있지는 않아요. **지출 한도 429**에는 절대 없고 접근이 다시 열릴 때까지 계속 실패하니, `error.details.error_code`가 `enforced_spend_limit_reached`인지 확인하세요.
- 속도 제한은 분당 요청 수, 입력 토큰, 출력 토큰으로 재고, 용량이 계속 채워지는 토큰 버킷 방식이에요. 대부분의 모델에서 캐시 읽기는 분당 입력 토큰에 포함되지 않아요.
- 스트리밍은 200 응답 **뒤에도** 실패할 수 있고, 그 오류는 이 규칙을 따르지 않아요.
- 2026-11-04에 공식 페이지 3개를 읽었고, 데모 스크립트의 판정 함수만 로컬에서 시험했어요. **실제 API 호출은 하지 못했어요**(API 키와 `anthropic` 패키지가 없었어요). 그래서 재시도 루프 자체는 여기서 확인하지 못했어요.
</Summary>

## 이 튜토리얼로 할 수 있게 되는 것

- 오류 응답을 읽고 요청을 고칠지, 기다렸다 재시도할지, 멈출지 판단해요.
- 일반 속도 제한 429와 지출 한도 429를 구별해요.
- 직접 재시도 코드를 쓰는 대신 SDK 내장 재시도를 쓰고, 직접 만든 층이 여전히 도움이 되는 경우를 알아요.
- 속도 제한 헤더와 `request-id`를 읽고 디버깅과 문의에 써요.

## 먼저 알아둘 개념

| 용어 | 뜻 |
| --- | --- |
| **일시적 오류** | 다시 시도하면 성공할 수 있는 실패. 연결 문제, 429, 5xx 등이에요. |
| **지수 백오프** | 실패할 때마다 기다리는 시간을 늘리는 방식. 예: 1초, 2초, 4초. |
| **`retry-after`** | 기다릴 초 수가 든 응답 헤더. 문서에 따르면 그보다 일찍 재시도하면 실패해요. |
| **토큰 버킷** | 문서에 따르면 속도 제한이 쓰는 알고리즘이에요. 정해진 시각에 초기화되지 않고 최대치까지 용량이 계속 채워져요. |
| **요청 ID** | `request-id` 헤더이자 오류 본문의 `request_id` 필드. 지원팀에 문의할 때 함께 보내세요. |

<Steps>

1. **오류 모양 읽기**

   모든 오류는 `type: "error"`, 자기 `type`과 `message`가 든 `error` 객체, 그리고 `request_id`가 있는 JSON이에요.

   ```json
   {
     "type": "error",
     "error": {
       "type": "not_found_error",
       "message": "The requested resource could not be found."
     },
     "request_id": "req_011CSHoEeqs5C35K2UUqR7Fy"
   }
   ```

   문서는 이 객체 안의 값이 시간이 지나며 늘어날 수 있다고 경고해요. `type` 값 목록이 닫혀 있다고 가정하지 마세요. 또 400 `invalid_request_error`는 목록에 없는 다른 4XX에도 쓰일 수 있어요.

2. **상태 코드를 세 묶음으로 나누기**

   이 묶음은 문서 설명을 제가 읽고 정리한 것이지, 문서에 있는 표가 아니에요.

   | 묶음 | 코드(문서의 이름) | 할 일 |
   | --- | --- | --- |
   | 요청이나 계정을 고친 뒤 다시 보내기 | 400 `invalid_request_error`, 401 `authentication_error`, 402 `billing_error`, 403 `permission_error`, 404 `not_found_error`, 413 `request_too_large` | 같은 요청을 다시 보내도 소용없어요. 형식, API 키, 콘솔의 결제 정보, 워크스페이스 권한, 엔드포인트 경로, 요청 크기를 확인하세요. |
   | 해결한 뒤 재시도 | 409 `conflict_error` | 문서는 충돌을 해결한 다음 재시도하라고 해요. |
   | 일시적, 백오프로 재시도 | 429 `rate_limit_error`, 500 `api_error`, 504 `timeout_error`, 529 `overloaded_error` | 문서는 500을 지수 백오프로 재시도하라고 하고, 429에 `retry-after`가 있으면 그 초만큼 기다리라고 해요. |

   문서에서 알아둘 점:

   - 400은 **내가 정한 지출 한도**에 닿았을 때도 돌아와요(메시지가 `You have reached your specified API usage limits`로 시작해요). 한도를 올리거나 없애면 더 빨리 복구돼요.
   - `CORS requests are not allowed for this Organization`으로 시작하는 401은 API 키 문제가 아니에요. 요청에 `Origin` 헤더(브라우저가 붙여요)가 있었고, 내 조직은 브라우저에서 API를 직접 호출할 수 없다는 뜻이에요. 요청을 직접 만든 백엔드에서 보내세요.
   - 529는 API가 일시적으로 과부하라는 뜻이고, 모든 사용자에게 트래픽이 몰릴 때 생길 수 있어요. 드물게 내 사용량이 갑자기 늘면 **가속 한도(acceleration limits)** 때문에 429가 나올 수 있으니 트래픽을 서서히 늘리세요.
   - 504 `timeout_error`는 다른 상태 코드와 함께 나올 수도 있어요. 예를 들어 응답이 시작되기 전에 서버 시간 제한에 닿으면 500으로 와요.
   - Messages API 요청 크기 한도는 128 MB예요(Batch API 256 MB, Files API 500 MB). 넘으면 413이 와요.

3. **먼저 SDK 재시도에 맡기기**

   흔한 경우에는 재시도 루프를 직접 쓸 필요가 없어요. 문서에 따르면 공식 SDK는 일시적 실패(연결 오류, 속도 제한, 5xx)를 지수 백오프로 기본 2번 다시 시도하고 `retry-after`를 따라요. Python SDK 페이지는 408과 409도 나열하고, 백오프가 짧다고 해요. 클라이언트나 요청 단위로 설정해요.

   ```python
   from anthropic import Anthropic

   client = Anthropic(max_retries=0)  # default is 2; 0 turns retries off

   client.with_options(max_retries=5).messages.create(
       max_tokens=1024,
       messages=[{"role": "user", "content": "Hello, Claude"}],
       model="claude-opus-5-5",
   )
   ```

   타임아웃은 별개예요. 기본은 10분이고 `timeout`으로 정하며, 타임아웃이 나면 `APITimeoutError`가 발생해요. 타임아웃된 요청도 기본 2번 재시도되니, 짧은 타임아웃에 재시도 횟수가 곱해져 오래 기다릴 수 있어요.

4. **SDK의 타입별 예외 잡기**

   SDK는 원본 JSON을 돌려주는 대신 `APIError`의 하위 클래스를 발생시켜요. 구체적인 클래스부터 잡고, 메시지 문자열 비교는 하지 마세요.

   | 상태 | Python 클래스 |
   | --- | --- |
   | 400 | `BadRequestError` |
   | 401 | `AuthenticationError` |
   | 403 | `PermissionDeniedError` |
   | 404 | `NotFoundError` |
   | 409 | `ConflictError` |
   | 422 | `UnprocessableEntityError` |
   | 429 | `RateLimitError` |
   | 500 이상 | `InternalServerError` |
   | 응답 없음 | `APIConnectionError` |

   다른 언어는 이름이 달라요. 오류 페이지에 각 SDK 페이지 링크가 있어요. Python 페이지는 `APIStatusError`에서 `e.status_code`와 `e.response`를 쓸 수 있다고 알려요.

5. **429는 두 종류예요**

   속도 제한 429는 속도 문제예요. 짧은 시간에 요청, 입력 토큰, 출력 토큰을 너무 많이 보냈다는 뜻이에요. 응답이 어느 한도인지 알려 주고, 보통 `retry-after`가 있어요. 기다리면 해결돼요.

   **지출 한도 429**는 돈 문제예요. 사용 등급의 월 지출 한도에 닿은 거예요. 문서가 밝힌 등급별 한도는 Start 월 $500, Build $1,000, Scale $200,000이고 Custom에는 없어요. 더 높은 한도를 받지 않으면 다음 달 1일 00:00 UTC까지 사용이 멈춰요. 오류 본문은 이렇게 생겼어요(메시지는 줄였어요).

   ```json
   {
     "type": "error",
     "error": {
       "type": "rate_limit_error",
       "message": "You have reached your API usage limits: ...",
       "details": { "error_code": "enforced_spend_limit_reached" }
     },
     "request_id": "req_018EeWyXxfu5pfWkrYcMdjWG"
   }
   ```

   타입은 같은 `rate_limit_error`지만 **`retry-after` 헤더가 없고**, SDK 자동 재시도를 포함해 어떤 재시도도 접근이 다시 열릴 때까지 실패해요. Messages API에서는 `error.details.error_code`로 구별해요. Claude Code 워크스페이스의 지출 한도는 따로 확인하고, `retry-after`가 붙은 429를 돌려줄 수도 있어요.

6. **작은 층을 직접 얹기**

   `safe_call.py`로 저장하세요. SDK 자체 재시도는 끄고(`max_retries=0`) 재시도 층을 하나만 두며, 재시도로 못 고치는 오류에서는 바로 멈추고, 나머지는 `retry-after`(없으면 1, 2, 4초)만큼 기다린 뒤 코드에서 한 번 더 시도해요. 지터(1초 미만의 무작위 값)는 문서가 아니라 흔히 쓰는 방법이에요.

   ```python
   import random
   import time

   import anthropic

   MODEL = "claude-opus-5-5"

   # The SDK already retries connection errors, 408, 409, 429 and >=500
   # 2 times by default (honoring retry-after). Here we turn that off.
   client = anthropic.Anthropic(max_retries=0)  # 재시도는 이 스크립트의 루프 한 층만


   def decide(status, headers, body):
       """Return (action, note). action is "fix", "stop", or "wait"."""
       error = (body or {}).get("error", {})
       code = (error.get("details") or {}).get("error_code")
       if status == 429 and code == "enforced_spend_limit_reached":
           return "stop", "Monthly spend cap reached. Retrying will keep failing."
       if status == 429 and "retry-after" not in headers:
           return "stop", "429 without retry-after. Check the message before retrying."
       if status in (400, 401, 402, 403, 404, 413):
           return "fix", f"{error.get('type')}: {error.get('message')}"
       if status in (429, 500, 504, 529):
           return "wait", f"{error.get('type')}: temporary"
       return "fix", f"unexpected status {status}"


   def ask(prompt, tries=3):
       for attempt in range(tries):
           try:
               return client.messages.create(
                   model=MODEL,
                   max_tokens=300,
                   messages=[{"role": "user", "content": prompt}],
               )
           except anthropic.APIStatusError as e:
               try:
                   body = e.response.json()
               except ValueError:
                   body = {}
               action, note = decide(e.status_code, e.response.headers, body)
               print(f"status {e.status_code} | request-id {e.response.headers.get('request-id')} | {note}")
               if action != "wait" or attempt == tries - 1:
                   raise
               seconds = float(e.response.headers.get("retry-after") or 2 ** attempt)
               time.sleep(seconds + random.random())  # small jitter
           except anthropic.APIConnectionError:
               print("could not reach the API")
               if attempt == tries - 1:
                   raise
               time.sleep(2 ** attempt)


   if __name__ == "__main__":
       reply = ask("Say hello in one short sentence.")
       print(reply.content[0].text)
   ```

   컴파일했고, 지어낸 상태 코드·헤더·본문으로 `decide`를 시험했어요. 지출 한도 본문은 "stop", `retry-after`가 있는 429는 "wait", 없는 429는 "stop", 529는 "wait", 400은 "fix"로 분류했어요. **루프는 실제 API로 실행하지 못했어요.** `e.response.json()`과 `e.response.headers`를 쓴 것은 Python SDK 페이지에 나온 `e.response` 속성을 따른 거예요. 그 밖의 본문 접근 방법은 확인하지 못했어요.

   여기서는 SDK 재시도를 껐으니 이 스크립트는 모두 합쳐 최대 3번만 시도해요. 반대로 SDK 재시도를 켜 둔다면 직접 만든 루프는 빼세요. 두 층을 겹치면 시도 횟수가 곱해지고(예: 3 x 5 = 15번) 장애 중에 부하를 더 키워요.

7. **속도 제한 헤더 읽기**

   모든 응답에는 한도, 남은 양, 다시 채워지는 시각을 알려 주는 헤더가 있어요. 문서가 나열한 헤더예요.

   | 헤더 | 뜻 |
   | --- | --- |
   | `retry-after` | 기다릴 초. 그보다 일찍 재시도하면 실패해요. 모든 429에 있지는 않아요 |
   | `anthropic-ratelimit-requests-limit` / `-remaining` / `-reset` | 요청 한도, 남은 요청 수, 다시 채워지는 시각(RFC 3339) |
   | `anthropic-ratelimit-input-tokens-limit` / `-remaining` / `-reset` | 입력 토큰의 같은 값(남은 양은 천 단위로 반올림) |
   | `anthropic-ratelimit-output-tokens-limit` / `-remaining` / `-reset` | 출력 토큰의 같은 값 |
   | `anthropic-ratelimit-tokens-*` | 지금 적용 중인 가장 엄격한 한도(워크스페이스 한도가 없으면 입력과 출력의 합계) |

   Python에서는 `client.messages.with_raw_response.create(...)`로 `response.headers`를 얻고, `response.parse()`가 평소의 메시지를 돌려줘요. `-remaining`이 낮아지면 잠깐 쉬는 식으로, 0이 되기 **전에** 속도를 늦추는 데 쓰세요. Priority Tier에는 `anthropic-priority-*` 헤더가 따로 있어요.

   한도를 올리려면 문서는 콘솔 Rate limits 페이지의 **Request tier increase**나 Anthropic 지원팀을 안내해요. 워크스페이스별로 더 낮은 한도를 정해 한 프로젝트가 조직 전체를 다 쓰지 못하게 할 수도 있어요. 내 등급과 한도는 콘솔 `platform.claude.com/usage/limits`에서 보여요. 제 쪽에서 내 숫자를 읽지 못했으니 거기서 확인하세요.

8. **한도에 닿는 횟수 줄이기**

   - **반복되는 부분은 캐시하세요.** 문서에 따르면 대부분의 모델에서 분당 입력 토큰에는 캐시되지 않은 입력만 들어가요. `input_tokens`와 `cache_creation_input_tokens`는 포함되고 `cache_read_input_tokens`는 포함되지 않아요. [개발 19](/ko/dev/19-prompt-caching/)를 보세요.
   - **기다려도 되는 일은 배치로 보내세요.** Message Batches API에는 자체 속도 제한이 있어요. [개발 16](/ko/dev/16-batch-api/)을 보세요.
   - **긴 출력은 스트리밍하세요.** 특히 10분이 넘는 긴 요청은 스트리밍이나 배치를 쓰라고 문서가 권해요. 유휴 연결을 끊는 네트워크가 있고, SDK는 스트리밍이 아닌 요청이 10분을 넘을 것으로 예상되지 않는지 검사해요. [개발 15](/ko/dev/15-streaming/)를 보세요.
   - **서서히 늘리세요.** 가속 한도를 피하려면요.

## 자주 막히는 부분

### 실패하기 전에 SDK가 멈춘 것 같아요

- **원인**: 호출 안에서 백오프를 둔 자동 재시도와 `retry-after` 대기가 일어나요. 기본 10분 타임아웃도 재시도되니, 호출 한 번이 타임아웃 한 번보다 훨씬 오래 걸릴 수 있어요.
- **해결**: 대화형 코드에서는 `max_retries`나 `timeout`을 낮추고, 실패마다 request-id와 함께 로그를 남기세요.

### 얼마를 기다려도 429가 계속 와요

- **원인**: 지출 한도 429일 수 있어요. `retry-after`가 없고 접근이 다시 열릴 때까지(또는 등급이 오를 때까지) 계속돼요. 내가 정한 지출 한도는 400으로 돌아와요.
- **해결**: `error.details.error_code`와 접근이 언제 돌아오는지 적힌 메시지를 확인하세요. 콘솔의 Billing 페이지와 등급을 살펴보세요.

### 400은 재시도해도 소용없어요

- **원인**: 요청 자체가 잘못됐거나 내가 정한 한도에 닿았어요.
- **해결**: `error.message`를 읽으세요. 문서에는 최신 모델에서 prefill 미지원, thinking 블록 수정, 모델이 받지 않는 thinking 설정 같은 흔한 검증 오류도 정리돼 있어요.

### 200을 받았는데 출력이 오류로 끊겼어요

- **원인**: 스트리밍(서버 전송 이벤트)에서는 200 응답 뒤에 오류가 날 수 있고, 표준 오류 처리 방식을 따르지 않아요.
- **해결**: 스트림 안의 오류 이벤트를 처리하세요. 스트리밍 문서의 Error events와 [개발 15](/ko/dev/15-streaming/)를 보세요.

### 브라우저 호출이 CORS 관련 401로 실패해요

- **원인**: 요청에 `Origin` 헤더가 있고, 내 조직은 브라우저에서 API를 호출할 수 없어요.
- **해결**: 직접 만든 백엔드에서 API를 호출하세요.

## 실전 팁

- 실패마다 `request-id`, 상태, `error.type`, 시각을 로그로 남기되, API 키나 개인정보가 든 프롬프트 전문은 남기지 마세요.
- "멈춤" 답을 받은 코드는 눈에 띄게 만드세요. 밤새 재시도하는 대신 사람에게 알리세요.
- 타임아웃된 요청은 처리됐을 수도 아닐 수도 있으니, 재시도되는 쓰기 작업이 내 시스템에서 같은 일을 두 번 하지 않게 할 방법을 두세요. 문서에 있는 내용이 아니라 일반적인 조언이에요.
- 필요해지기 전에 실패 경로(예: 잘못된 API 키)를 일부러 시험해 보세요.
- 지출 한도와 속도 제한은 비용 관리와 이어져요. [개발 2](/ko/dev/02-cost-optimization/)와 [개발 11](/ko/dev/11-usage-cost-api/)을 보세요.
