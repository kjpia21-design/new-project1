<Summary>
- Message Batches API는 Messages 요청 목록을 받아 **비동기**로 처리하고, 입력과 출력 모두 표준 가격의 **50%**만 받아요. 공식 문서는 대부분의 배치가 1시간 안에 끝난다고 해요.
- 요청마다 고유한 `custom_id`(1~64자, 영문·숫자·하이픈·밑줄)와 일반 Messages 매개변수가 든 `params` 객체가 있어요.
- 문서의 한도: 배치 하나에 **요청 100,000건 또는 256MB**(먼저 닿는 쪽), 24시간 안에 끝나지 않으면 **만료**, 결과는 생성 후 **29일** 동안 내려받을 수 있어요.
- 흐름: 배치 생성, `processing_status`가 `ended`가 될 때까지 폴링, `.jsonl` 결과 읽기. 결과는 **어떤 순서로든** 올 수 있으니 `custom_id`로 맞추세요.
- 결과 종류: `succeeded`, `errored`, `canceled`, `expired`. 뒤의 셋은 **과금되지 않아요**. 배치에서 쓸 수 없는 것: `stream: true`, `speed`, `fallbacks`, `max_tokens: 0`.
- 문서상 배치는 제로 데이터 보존(ZDR) 대상이 아니고(29일 보존) Managed Agents에서는 쓸 수 없어요.
- 2026-11-02에 공식 배치 처리 페이지를 읽었고, 스크립트의 결과 매칭 로직을 로컬 스텁으로 실행했어요. 하지만 **실제 API 호출은 하지 못했어요**(API 키와 `anthropic` 패키지가 없었어요). SDK 코드는 문서 기준이고 끝까지 테스트하지 않았어요. 가격은 2026-11-02 기준이에요.
</Summary>

## 이 튜토리얼로 할 수 있게 되는 것

- 작업이 배치에 맞는지(대량이고 급하지 않음), 일반 호출이 필요한지 판단해요.
- 요청을 한꺼번에 제출하고 답을 안전하게 모아요.
- 실패·취소·만료된 요청을 요금 걱정 없이, 놓치지 않고 처리해요.
- 배치로 얼마나 아끼는지 계산해요.

## 먼저 알아둘 개념

일반 호출은 요청 하나를 보내고 답을 기다려요. 배치는 요청을 여러 개 묶어 보내고, Anthropic이 각각을 독립적으로 처리하면 나중에 결과를 가져가요. 공식 문서가 드는 예는 대규모 평가, 콘텐츠 검수, 데이터 분석, 대량 콘텐츠 생성이에요. 사람이 기다리는 작업에는 맞지 않아요.

| 용어 | 뜻 |
| --- | --- |
| **배치(Batch)** | 함께 제출한 Messages 요청 묶음이에요. `msgbatch_`로 시작하는 `id`가 있어요. |
| **`custom_id`** | 요청 하나에 붙이는 내 라벨이에요. 결과를 요청과 맞추는 유일하게 믿을 수 있는 방법이에요. |
| **`processing_status`** | `in_progress`에서 `ended`로 바뀌어요. (취소를 요청하면 먼저 `canceling`이 돼요.) |
| **`request_counts`** | 처리 중·성공·오류·취소·만료된 요청 수예요. |
| **워크스페이스(Workspace)** | 배치는 만든 Console 워크스페이스에 속하고, 그 워크스페이스에서만 볼 수 있어요. |

[개발 2](/ko/dev/02-cost-optimization/)에서 소개한 50% 할인, [개발 14](/ko/dev/14-token-counting/)의 보내기 전 비용 추정과 이어지는 내용이에요. 스트리밍([개발 15](/ko/dev/15-streaming/))은 반대쪽 선택이에요. 빠르고 실시간이 스트리밍, 느리지만 저렴한 것이 배치예요.

<Aside type="caution" title="배치로 보내기 전에 개인정보 확인">
공식 문서는 Message Batches API를 **제로 데이터 보존 대상 아님**, **HIPAA 대상 아님**으로 적어요. 배치의 입력과 출력은 최대 29일 동안 저장돼요. 조직에 별도 데이터 규정이 있다면 민감한 데이터를 보내기 전에 담당자와 문서의 데이터 처리 페이지를 확인하세요.
</Aside>

<Steps>

1. **작업이 맞는지 확인하기**

   잘 맞는 경우: 서로 독립적인 요청이 많고 기다리는 사람이 없는 작업. 맞지 않는 경우: 채팅처럼 상호작용하는 작업. 기억할 한도: 배치 하나에 **요청 100,000건 또는 256MB**, **24시간** 안에 끝나지 않으면 만료돼요. 데이터가 아주 크면 여러 배치로 나누라고 문서가 권해요. 대기열에 둘 수 있는 요청 수 제한은 별도의 한도 페이지에 있는데 열어보지 못했어요(확인하지 못함).

   비전, 도구 사용(서버 도구 포함), 시스템 메시지, 멀티턴 대화, 확장 사고 등 거의 모든 Messages 요청을 배치에 넣을 수 있고, 한 배치에 서로 다른 종류를 섞어도 돼요. 예외는 `stream: true`, `speed`(빠른 모드), `fallbacks`(서버 측 폴백), `max_tokens: 0`이에요. 요청마다 `max_tokens`는 1 이상이어야 해요.

2. **요청 하나를 먼저 테스트하기**

   문서에 따르면 요청별 `params` 검증은 **비동기**로 이뤄져서, 실수가 배치 전체가 끝난 뒤에야 드러나요. 같은 형태의 요청 하나를 일반 Messages API로 먼저 보내 보세요.

3. **배치 만들기**

   각 항목은 `custom_id`와 `params`를 가진 `Request`예요. 여기서는 모델이 짧은 상품 리뷰 세 개를 읽어요. `run_batch.py`로 저장하세요. 3~5단계를 모두 담고 있어요.

   ```python
   import time

   import anthropic
   from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
   from anthropic.types.messages.batch_create_params import Request

   client = anthropic.Anthropic()

   reviews = {
       "review-001": "The battery lasts two days, but the strap broke in a week.",
       "review-002": "Fast shipping and the screen is gorgeous.",
       "review-003": "Support never answered my refund request.",
   }

   # 1. 배치 만들기: 항목마다 고유한 custom_id를 가진 Request 하나
   batch = client.messages.batches.create(
       requests=[
           Request(
               custom_id=cid,
               params=MessageCreateParamsNonStreaming(
                   model="claude-opus-5-5",
                   max_tokens=200,
                   messages=[{
                       "role": "user",
                       "content": f"Classify this review as positive, negative, or mixed. One word only.\n\n{text}",
                   }],
               ),
           )
           for cid, text in reviews.items()
       ]
   )
   print("생성됨", batch.id, batch.processing_status)

   # 2. 배치 전체가 끝날 때까지 폴링
   while True:
       batch = client.messages.batches.retrieve(batch.id)
       if batch.processing_status == "ended":
           break
       print("처리 중...", batch.request_counts)
       time.sleep(60)

   # 3. 결과 읽기. 순서는 보장되지 않으니 custom_id로 맞춰요.
   labels, to_retry = {}, []
   for result in client.messages.batches.results(batch.id):
       outcome = result.result
       if outcome.type == "succeeded":
           labels[result.custom_id] = outcome.message.content[0].text
       elif outcome.type == "errored" and outcome.error.error.type != "invalid_request_error":
           to_retry.append(result.custom_id)  # 서버 오류: 다시 시도 가능
       else:
           print("확인 필요:", result.custom_id, outcome.type)

   print(labels)
   print("나중에 재시도:", to_retry)
   ```

   `create`는 곧바로 돌아오고 `processing_status: "in_progress"`, `results_url`은 `null`이에요. cURL은 `x-api-key`, `anthropic-version: 2023-06-01` 헤더와 함께 `https://api.anthropic.com/v1/messages/batches`에 `{"requests": [...]}`를 보내요. 문서에는 `ant messages:batches create` CLI 형태도 있어요.

4. **배치가 끝나길 기다리기**

   위 반복문이 문서의 폴링 방식이에요(문서는 확인 사이에 60초를 쉬어요). Console에서 배치를 볼 수도 있어요. 대부분 1시간 안에 끝나지만, 수요와 내 요청량에 따라 처리가 느려질 수 있고 그러면 24시간 뒤 만료되는 요청이 늘 수 있다고 문서가 알려줘요.

5. **결과를 읽고 `custom_id`로 맞추기**

   결과는 `.jsonl`이고 요청마다 한 줄이에요. 문서의 예시에서는 두 번째 요청의 답이 첫 번째보다 먼저 나오고, 순서가 요청 순서와 다를 수 있다고 분명히 적혀 있어요. 결과 종류는 네 가지예요.

   | 결과 | 뜻 | 과금 |
   | --- | --- | --- |
   | `succeeded` | 메시지가 만들어졌어요. | 과금됨 |
   | `errored` | 잘못된 요청이거나 내부 오류예요. | 과금 안 됨 |
   | `canceled` | 모델에 보내기 전에 내가 취소했어요. | 과금 안 됨 |
   | `expired` | 그 전에 24시간이 지났어요. | 과금 안 됨 |

   `errored`에 대해 문서의 예시는 `invalid_request_error`면 "요청 본문을 고친 뒤 다시 보내기", 다른 오류면 "바로 재시도 가능"으로 다뤄요. 요청 하나가 실패해도 다른 요청에는 영향이 없어요. 배치 결과는 배치를 만든 요청의 API 버전을 따라요.

6. **취소·삭제·정리**

   `POST /v1/messages/batches/{id}/cancel`(SDK: `client.messages.batches.cancel(id)`)을 부르면 `canceling`을 거쳐 `ended`가 되고, 부분 결과가 있을 수 있어요. 제출한 배치는 **수정할 수 없어요**. 취소하고 다시 제출하세요. 취소가 즉시 적용되지 않을 수도 있어요. 처리가 끝난 뒤에는 `DELETE /v1/messages/batches/{id}`로 삭제할 수 있고, 진행 중인 배치는 먼저 취소해야 해요. 목록 조회 엔드포인트도 있고 페이지 나눔(`has_more`, `after_id`)을 쓰며, SDK는 자동으로 다음 페이지를 가져와요.

7. **캐싱으로 더 아끼기(선택)**

   프롬프트 캐싱은 배치에서도 되고 할인이 겹칠 수 있어요. 다만 요청이 동시에, 순서 없이 처리되므로 캐시 적중은 **최선 노력** 수준이고, 문서는 적중률이 보통 30~98% 범위라고 해요. 모든 요청에 같은 `cache_control` 블록을 넣고, 배치는 5분보다 오래 걸릴 수 있으니 1시간 캐시를 쓰라고 권해요. 캐싱 기초는 [개발 2](/ko/dev/02-cost-optimization/)를 보세요.

   <PromptBox>
   [CSV/JSON/데이터베이스]에 항목이 [N]개 있고, 항목마다 Claude가 [작업]을 하게 하고 싶어요. anthropic SDK로 항목마다 고유한 custom_id를 붙인 Message Batch 하나를 만들고, 끝날 때까지 폴링한 뒤, 결과를 custom_id별로 파일에 저장하고 오류 또는 만료된 항목을 모두 나열하는 Python 스크립트를 써 주세요. 공식 배치 처리 페이지에 문서화된 기능만 쓰고 모델은 claude-opus-5-5를 쓰세요.
   </PromptBox>

</Steps>

## 배치로 얼마나 아끼나 (2026-11-02 기준)

문서는 배치 사용량을 입력 토큰, 출력 토큰, 특수 토큰 모두 **표준 가격의 50%**로 청구한다고 해요. 문서 표의 배치 가격은 100만 토큰당 다음과 같아요.

| 모델 | 표준 입력 / 출력 (개발 2) | 배치 입력 / 출력 |
| --- | --- | --- |
| Opus 5.5 (`claude-opus-5-5`) | $4 / $20 | $2 / $10 |
| Sonnet 5.5 (`claude-sonnet-5-5`) | $2 / $10 | $1 / $5 |
| Haiku 5.5, 프롬프트 100,000토큰 이하 | $0.10 / $0.50 | $0.05 / $0.25 |
| Haiku 5.5, 프롬프트 100,000토큰 초과 | $0.50 / $2.50 | $0.25 / $1.25 |

**계산 예시(API 결과가 아니라 우리가 직접 계산한 값):** 요청 10,000건, 각각 입력 약 1,000토큰·출력 약 200토큰, Sonnet 5.5. 입력 1,000만, 출력 200만 토큰이에요. 표준: 10 x $2 + 2 x $10 = **$40**. 배치: 10 x $1 + 2 x $5 = **$20**. 실제 토큰 수는 [개발 14](/ko/dev/14-token-counting/)로 세세요. 가격은 바뀔 수 있으니 의존하기 전에 공식 가격 페이지를 확인하세요(배치 페이지도 claude.com/pricing을 안내해요). 별도의 가격 페이지는 열어보지 못했어요.

## 자주 막히는 부분

### 검증 오류가 몇 시간 뒤에야 보여요

- **원인**: `params`가 비동기로, 배치가 끝난 뒤에 검증돼요.
- **해결**: 같은 형태의 요청 하나를 일반 Messages API로 먼저 보내 보세요.

### 413 `request_too_large` 오류가 나요

- **원인**: 배치가 256MB(또는 요청 100,000건)를 넘었어요.
- **해결**: 더 작은 여러 배치로 나누세요.

### 결과 순서가 뒤죽박죽이에요

- **원인**: 문서에 따르면 결과는 어떤 순서로든 올 수 있어요.
- **해결**: 항상 `custom_id`로 찾으세요.

### 많은 요청이 `expired`로 왔어요

- **원인**: 24시간 안에 모델로 보내지지 못했어요. 문서는 수요와 내 요청량이 처리를 늦출 수 있다고 해요.
- **해결**: 만료된 요청만 새 배치로 다시 제출하세요. 만료분은 과금되지 않았어요.

### 결과를 내려받을 수 없어요

- **원인**: 배치가 **생성된** 지 29일이 지났거나(끝난 때부터가 아니에요), 조직이나 워크스페이스에서 Console 다운로드를 꺼 뒀어요.
- **해결**: 배치가 끝나면 곧바로 결과를 내 저장소에 보관하세요.

### 합계가 지출 한도를 조금 넘었어요

- **원인**: 문서에 따르면 높은 처리량과 동시 처리 때문에 배치가 워크스페이스 지출 한도를 조금 넘길 수 있어요.
- **해결**: 한도에 여유를 두세요.

## 실전 팁

- `custom_id`는 행 ID처럼 의미 있는 값으로 하면 나중에 어떤 항목이든 찾기 쉬워요.
- 결과 스트림을 읽는 대로 `custom_id`별로 디스크에 저장하고, 재시도가 필요한 목록을 따로 관리하세요.
- 실시간 기능은 일반 API에 두세요. 배치는 아무도 기다리지 않는 작업용이에요.
- 큰 배치 전에 개발 14로 추정하고, 요청 몇 개짜리 작은 배치를 먼저 돌려 보세요.
- 실제 배치는 실행하지 못했어요. 첫 실행은 테스트로 보고 결과를 직접 확인하세요.
