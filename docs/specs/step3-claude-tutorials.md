## 공통 규칙

**먼저 읽을 것**
- `docs/specs/step2-samples.md`: 표준 구조, 사실 정확성 규칙, 문체가 여기 있다. **이번에도 그대로 적용한다.**
- `docs/templates/tutorial-template.mdx`: 템플릿.
- 완성된 샘플 `src/content/docs/claude/c02-plans-limits.mdx`, `c13-cloud-sessions.mdx`: 이 수준의 깊이와 형식을 맞춘다.

**사실 정확성**
- 근거는 담당 편에 맞는 `docs/research/claude/Cxx-*.md`만 쓴다.
- 연구 파일에 없는 내용은 공식 페이지(code.claude.com, support.claude.com, claude.com, platform.claude.com, docs.claude.com, anthropic.com)를 WebFetch로 직접 읽은 경우에만 쓰고, 그 URL을 `sources`에 넣는다. 기억으로 채우지 말 것.
- 연구 파일에서 "검색 요약"으로 표시된 내용은 확인 가능하면 WebFetch로 원문을 확인한다. 확인하지 못하면 단정하지 말고 "공식 도움말에서 최신 내용을 확인하세요"로 처리한다.
- 연구 파일의 "확인 못 함 / 주의"는 본문에서 단정하지 말 것.
- 자주 바뀌는 정보(가격, 버전, 플랜별 제공 여부, 베타 여부)에는 "2026-10-10 기준"을 붙인다.
- 특정 개인 계정 정보는 절대 쓰지 말 것.

**형식**
- 기존 placeholder 파일을 **같은 파일명 그대로** 덮어쓴다. frontmatter의 title, sidebar.label, level, category는 유지한다. 단 title이 내용과 맞지 않으면 다듬어도 된다.
- `status: published`, `lastVerified: 2026-10-10`, `sources`에는 실제로 근거로 쓴 출처만 넣는다. `duration`, `prerequisites`, `tools`는 내용에 맞게 다시 쓴다.
- 구조는 9개 섹션이다: 요약 → 할 수 있게 되는 것 → 개념 → 따라하기 → 빠른 참조표 → 막히는 지점 → 실전 팁 → 다음 튜토리얼 → 출처(자동).
  - 따라하기가 맞지 않는 개념형 주제(C1 등)는 "직접 해보기"로 가볍게 바꿔도 된다.
- 도식은 꼭 도움이 될 때만 넣는다. 넣는다면 `src/components/diagrams/`에 **편 번호를 붙인 새 파일**로 만든다(예: `C01ModelMap.astro`). 기존 컴포넌트는 수정 금지.
- 내부 링크는 `/new-project1/claude/<파일명>/` 형식으로 쓴다. 다른 편으로 가는 링크도 적극적으로 넣는다(파일명은 아래 표 참고).

**작업 범위**
- 수정 가능한 파일: 내가 맡은 `.mdx` 파일, 그리고 내가 새로 만든 도식 컴포넌트뿐이다.
- 그 밖의 파일(컴포넌트, 설정, PLAN, research, 다른 편)은 건드리지 말 것.
- 공통 컴포넌트 수정이 필요하면 직접 고치지 말고 보고서에 적는다.
- **git 커밋·푸시 금지.** 기획 담당이 검토 후 커밋한다.
- 끝나면 `npm run build`로 빌드 성공과 링크 검사 통과를 확인한다. 다른 에이전트가 동시에 작업 중이라 그쪽 파일 때문에 빌드가 실패할 수 있는데, 그 경우 내 파일에서 난 오류가 아니면 보고만 한다.
- 스크린샷은 찍지 않아도 된다. 기획 담당이 전체를 모아서 찍는다.

## 편별 지시

- **C1**: 현재 모델 4종(Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5)을 비교표로 정리한다. 상황별로 어떤 모델을 고를지 가이드를 넣는다. 공식 권장 기본값(Opus 5.5)을 소개하고, Fable은 기본값이 아니라 직접 골라야 한다는 점을 설명한다. 모델 ID와 API 가격은 C16과 일관되게 쓴다.
- **C3**: 웹·데스크톱(Mac/Windows)·모바일(iOS/Android) 앱의 차이를 설명한다. Chat과 Cowork 통합 출시 같은 최근 변화는 연구 파일 근거대로 쓰고 "2026-10-10 기준"을 붙인다.
- **C4**: 공식 프롬프트 가이드를 실무 예시로 풀어 쓴다. 같은 요청의 나쁜 예와 좋은 예를 비교하는 PromptBox를 넣는다. 예시는 회의록 요약, 보고서 초안, 데이터 정리처럼 한국 직장인이 공감할 업무로 고른다.
- **C6**: 공유(Share)와 예전 방식인 게시(Publish, 2026-09-16 이전 아티팩트)를 구분해 설명한다. 게시를 취소하면 되돌릴 수 없다는 점을 경고하고, 안에서 AI가 동작하는 아티팩트도 다룬다.
- **C7**: Notion 연결 절차는 공식 근거가 약하다. 단정하지 말고 일반 절차와 함께 "화면 안내에 따르세요"로 처리한다.
- **C8**: 스킬 파일 이름이 문서마다 `skill.md`와 `SKILL.md`로 다르게 적혀 있다. 두 표기를 모두 소개하고, Claude Code 문서 기준은 `SKILL.md`라고 밝힌다. 간단한 스킬을 직접 만들어 보는 예제를 넣는다.
- **C11**: 컴퓨터 사용이 어떤 플랜에서 되는지, 베타 여부, 지원 OS는 "2026-10-10 기준"을 붙여 쓰고, 문서 사이에 다른 점이 있으면 밝힌다. 안전 수칙(민감 정보, 금융 동작)을 강조한다.
- **C12**: 설치부터 첫 작업까지 따라하기로 구성한다. 터미널, IDE, 데스크톱, 웹 중 어디서 쓸지 고르는 법을 넣고, C13·C14로 연결한다.
- **C14**: 다룰 기능은 CLAUDE.md, 슬래시 명령, 훅, 서브에이전트, MCP, 권한 모드, 계획 모드, 스킬이다. 각 기능마다 "언제 쓰나 + 최소 예시"를 넣는다. 고급 편이므로 설정 파일 예시는 코드 블록으로 보여준다.
- **C15**: 공식 근거(`opusplan` 별칭, 서브에이전트 모델 결정 순서, 비용 안내)를 먼저 설명한다. 그다음 **이 사이트 제작 사례**를 실제 워크플로로 보여준다. 사례의 사실관계는 아래와 같고, 이 밖의 내용은 지어내지 말 것.
  - 사용자는 클라우드 세션 하나에서 Opus 5.5에게 기획을 맡기고, 구현은 Sonnet 5.5 하위 에이전트(Agent 도구의 model 파라미터로 지정)가 하도록 나눴다.
  - Opus의 일: 질문으로 요구사항 정리 → `docs/PLAN.md` 작성 → 단계별 작업 명세(`docs/specs/step1-skeleton.md`, `step2-samples.md`, 이 파일)를 작성 → 하위 에이전트 실행 → 결과 검토(스크린샷 확인, 사실 대조) → 작은 수정은 직접 함 → 커밋·PR.
  - Sonnet의 일: 1단계에서는 사이트 구현과 공식 문서 조사를 **두 에이전트가 병렬로** 진행했다. 2단계에서는 템플릿과 샘플 2편을 썼다. 3단계(이번)에서는 에이전트 4명이 14편을 나눠 쓴다.
  - 검토에서 실제로 잡아낸 예시:
    - 홈 제목이 두 번 나오는 버그. 원인은 홈 페이지 id 판별 조건이었다.
    - 조사 에이전트가 "클라우드 세션 크레딧은 없다"고 결론 냈지만, 실제 설정 화면에는 그 항목이 표시되어 있었다. 이 차이를 "공식 문서 미반영 항목"으로 정리했다.
  - 교훈:
    - 명세가 구체적일수록 하위 에이전트 결과가 좋다.
    - 사실 확인과 최종 판단은 기획 모델이 맡는다.
    - 하위 에이전트는 커밋하지 않게 하고 기획 쪽에서 모아 커밋하면 충돌이 없다.
  - 직접 따라 할 수 있는 예시 명세 템플릿을 PromptBox로 제공한다.
- **C16**: Console에서 키 발급 → curl과 Python으로 첫 호출 → 가격 안내 순서로 구성한다. 예시 코드는 공식 quickstart를 기준으로 하고, 모델 ID는 연구 파일의 값을 쓴다. API 키를 코드에 직접 넣지 말라는 보안 주의를 넣는다.
